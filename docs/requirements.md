# 技術インフラ要件定義書（Basetract）

## 1. プロジェクト概要
本プロジェクトは、CCNA、Linux、Oracle、プログラミング等のあらゆる学習システムを迅速に展開するための、標準化された高品質なインフラ基盤（Basetract）を提供します。

## 2. インフラの理念
本システムは、拡張可能な「基盤」として設計されています：
- **抽象化**: データ構造（JSON/JS）とプレゼンテーション層（HTML/CSS）を完全に分離。
- **拡張性**: 新しいデータモデル、自動化ツール、カスタムインターフェースの容易な統合。

## 3. 機能要件

### 3.1 オーケストレーション層 (Factory)
- 単一コマンドによるディレクトリ構造とテンプレートファイルの自動生成。
- プロジェクト固有のプレースホルダーの自動置換による即時開発環境の提供。

### 3.2 品質保証 (Quality Guard & Detector)
- AIによるハルシネーション（知ったかぶり）の検知と、ルールベースによる物理検証。
- 解析密度（100文字以上の詳細解説）の強制による、高エントロピーな学習コンテンツの担保。

### 3.3 リサーチ・パイプライン
- 公式ドキュメントURLからの技術データ自動収集。
- 収集データの自動セグメント変換（Factory および `content_generator.py`）。

### 3.4 プレゼンテーション層 (Standard UI)
- HTML5/CSS3/JSをベースとした、特定のブランドに依存しない標準的な学習UI。
- Mermaid.jsによる技術図解の動的描画と、モジュール式データの読み込み。
- **レスポンシブ・レイアウト (Verified Responsive)**: スマホ・タブレット等の小画面においても、サイドバーの圧殺やレイアウト破綻を許さない強固なレスポンシブ制約（Nuclear CSS等）を基盤テンプレートレベルで保証すること。
- **動的ナビゲーション**: ユーザー主導のサイドバー開閉および、インライン演習（Mini-Quiz）による双方向学習体験の提供。

### 3.5 アプリケーション・パッケージング
- **デスクトップ・ランチャー**: Python/PyWebViewによる、ブラウザに依存しない独立ウィンドウでの学習体験提供。
- **ユニバーサル・エンジン**: Flaskベースの軽量バックエンドによる、ローカル環境での高度なデータ処理（API連携、DB永続化）の実現。

### 3.6 AI Agent Team Development Framework
- **協調開発アーキテクチャ**: 単一AIによる開発から、役割ベースのAI Agent Teamによる協調開発へ移行
- **チーム構成**: 監督・監査エージェント(1)、開発エージェント(3)、品質保証エージェント(2)の1:3:2比率
- **反復品質保証サイクル**: Module 1（伝統的Basetract品質検証）とModule 2（辛辣自己レビュー）の2段階検証
- **紛争解決メカニズム**: エージェント間の意見対立時の調整とエスカレーションプロセス
- **柔軟な役割ル配分**: プロジェクト複雑度に応じた動的なチームサイズ調整
- **標準化されたコミュニケーションプロトコル**: エージェント間の情報伝達と調整の統一化
- **リスクベース品質評価**: プロジェクトリスクに応じた品質保証サイクル数の動的調整
- **絶対参照ドキュメント**: `docs/ai_agent_framework.md`, `docs/ai_agent_base_prompt.md`, `docs/ai_agent_example.md`

## 4. 非機能要件

### 4.1 保守性
- AIによる自律的な保守・更新を想定した、厳密な技術仕様（Specification）の定義。

### 4.2 ポータビリティ
- macOS, Linux, Windows (WSL) 環境での動作。
- 標準的なPythonライブラリとブラウザ標準技術への依存。

## 5. 今後の拡張性
- マルチモデルAIによるタスクルーティング。
- SQLiteベースの学習履歴アナリティクス。
- コンテナ化されたハンズオン・ラボ環境の統合。
- **クオリティ監査レベルの動的切り替え**（`config/quality_profiles.json` + `tools/quality_config.py` + `materials/quality_dashboard.html` にて実装済み）。

## 5-B. 自己改良システム 拡張ロードマップ（一案）

> **位置づけ**: これはBasetractを使用した各アーキテクチャに将来的に追加可能な拡張例。現時点では実装不要。アーキテクチャの方向性として記録する。
> **前提条件**: システム停止ゼロを必達とする。

### 概念

Basetractの「AIが保守できる品質ゲート」という設計哲学を自己監視・自己修復に発展させる。
`quality_reporter.py`が出力するPROJECT_HEALTH.mdは、すでに「システムの自己診断結果」として機能している。
この診断結果をトリガーに、段階的な自己改良ループを構築することが目標。

### 段階的実装ロードマップ

**Level 1 — パラメータ自動チューニング（設定値の自動調整）**
- 実現難易度: ★☆☆（容易）
- ダウンタイム: なし（設定ファイル書き換えのみ）
- 実装コスト: 1〜3日
- 内容: `quality_reporter.py`の統計（拒否率・平均logicスコア等）を読み、`quality_profiles.json`の閾値を自動調整するObserverスクリプト。`watchdog`ライブラリで設定ファイル変更を検知→Flaskが自動リロード。
- 既存ツールへの変更: `quality_guard.py`と`hallucination_detector.py`が`quality_config.get_active_profile()`を呼ぶように修正するのみ（ai_correction_instructions.md タスク4参照）。

**Level 2 — モジュールホットスワップ（コードの部分置換）**
- 実現難易度: ★★☆（中程度）
- ダウンタイム: 数ms（処理中リクエストが終わるまで待機）
- 実装コスト: 1〜2週間
- 内容: AI（Claude API等）がパッチコードを生成→`py_compile`で構文チェック→`importlib.reload(module)`でホットスワップ→失敗時は即ロールバック。
- 対象モジュール: `tools/quality_guard.py`、`tools/hallucination_detector.py`（ビジネスロジックのみ。Flaskルーティング・DBスキーマは対象外）。

**Level 3 — AI生成コード＋Blue-Greenデプロイ（完全自律修正）**
- 実現難易度: ★★★（高）
- ダウンタイム: 0ms（nginxのプロキシ切り替えのみ）
- 実装コスト: 1〜2ヶ月
- 内容: 2つのFlaskインスタンスをnginxで管理。Aが稼働中にBで新コードをテスト→CI相当のテスト通過後にnginxをBに向け替え→旧Aをスタンバイに。SQLiteはWALモードで両インスタンスが同時アクセス可能。
- ハードウェア要件: RAM 2GB以上（2インスタンス同時起動のため）。

**Level 4 — アーキテクチャ変更**
- 実現難易度: 現時点では非現実的（AGIレベル）
- 扱い: スコープ外。将来の検討事項として記録のみ。

### コスト試算（参考）

| 構成 | ハードウェア | LLM API費用（月） | 合計（月） |
|---|---|---|---|
| Level 1（設定自動チューニング） | 既存PCで可 | $0.1〜1 | $0〜1 |
| Level 2（モジュールホットスワップ） | RAM 2GB以上 | $1〜10 | $1〜10 |
| Level 3（Blue-Green / VPS） | VPS $20〜40 | $5〜30 | $25〜70 |

### 注意事項

- 完全自律修正（Level 2〜3）を開始する前に、**人間承認ゲート**（AIが修正案を提示→人間がワンクリック承認）を経由する設計を強く推奨する。
- 実績が積まれてから段階的に自律化の範囲を広げること。
- データベーススキーマの変更は自動修正の対象から除外すること（必ずダウンタイムが発生するため）。

## 6. 設計理念（他システムへの応用）

> **追記日**: 2026-03-22

### 6.1 Basetractの設計理念

Basetractの核心は以下の3つの設計哲学にある：

1. **データ・プレゼンテーション分離原則**: コンテンツ（JSON/JS）とUI（HTML/CSS）を完全に分離することで、片方を変えても他方への影響を最小化する。
2. **AIが保守できる品質ゲート**: 人間が定めたルール（スキーマ・文字数・キーワード照合）を機械的に検証するツールを整備し、AIが安全に自律保守できる環境を提供する。
3. **Responsive思想**: あらゆる想定外の入力（長文・複雑な表・コード）に対しても、UIが壊れない「技術的堅牢性」を最優先とする。

### 6.2 他のシステムへの流用可能性

Basetractのアーキテクチャは、以下の条件を持つシステムであればそのまま流用できる：

- AIが生成したコンテンツを品質管理したい
- コンテンツとUIを分離してモジュール管理したい
- 多デバイス（PC/モバイル）対応が必要

### 6.3 流用可能なシステム例と要件定義への組み込み方

**例1: 医療・法律知識ベースシステム**
- Basetractの12キースキーマを「医療用語集スキーマ」に転用（`logic`→「エビデンスレベルと文献参照」、`textbook_ref`→「ガイドライン章番号」）
- `hallucination_detector.py`の「キーワード照合」を医療エビデンスの引用チェックに流用
- Responsive Layoutと同等のレスポンシブ設計を維持（モバイル閲覧に対応）
- 応用要件定義: 「logicフィールドは必ずICD-10コードまたは医学的エビデンスグレード(A〜D)を含むこと」

**例2: 法令・規制コンプライアンス学習システム**
- `category`フィールドを「法令種別（労働基準法・個人情報保護法等）」に置き換え
- `research_crawler.py`を官公庁e-govサイトへのクローリングに転用
- `textbook_ref`を「法律の条番号（第XX条第XX項）」として運用
- 応用要件定義: 「logicフィールドは必ず条文番号を含み、法改正日と施行日を明記すること」

**例3: 製品マニュアル・社内ナレッジベースシステム**
- `factory.py`の「プロジェクト生成」機能を「製品ラインごとのナレッジベース展開」に転用
- `project_registry.json`で複数製品のバージョン別ナレッジを一元管理
- `quality_reporter.py`の出力（`PROJECT_HEALTH.md`）を製品別ドキュメント更新状況の自動レポートに転用
- 応用要件定義: 「各エントリのlogicフィールドは製品バージョン番号と対象ファームウェアを必須とする」

**例4: セキュリティ教育・ペンテスト訓練システム**
- `difficulty`フィールドをCVSS評点と連動させる（Easy=CVSS 0〜3、Medium=4〜6、Hard=7〜10）
- `options`を攻撃手法の選択肢として活用（CTF形式の演習問題生成に流用）
- `hallucination_detector.py`の「answer exists in options」チェックをそのまま転用
- 応用要件定義: 「logicフィールドはCVE番号またはMITRE ATT&CK Technique IDを含むこと」

**例5: 語学学習（TOEIC・英検・N1等）システム**
- `text`を「英文問題文」、`logic`を「文法解説+誤答の文法的理由」に転用
- `quality_guard.py`のlogic密度チェックを「解説が文法タグ（品詞名・構文名）を3つ以上含むか」に調整
- `research_crawler.py`を英語辞書API・語彙リストサイトへのクローリングに転用
- 応用要件定義: 「logicフィールドは必ず品詞表記（名詞句、関係詞節等）と反意語/類義語を含むこと」

### 6.3-B 非学習系への展開（ゲーム・自己分析）

> **追記日**: 2026-03-22

#### 前提：なぜゲーム・自己分析にも使えるか

Basetractの12キースキーマは「問い→選択肢→正解→解説→行動プラン」という構造を持つ。この構造は「ユーザーに何かを問い、反応を処理し、フィードバックを返す」という**あらゆる対話型インタラクションの汎用モデル**でもある。ゲームのクイズ・チャレンジも自己分析の設問も、この構造に完全に収まる。

品質ゲート（`hallucination_detector.py` / `quality_guard.py`）はドメインを問わず「コンテンツが十分な深さと一貫性を持つか」を検証する機構であり、ゲームコンテンツや自己分析の設問品質にも同様に適用できる。

---

**例6: インタラクティブ・クイズゲームシステム**

**適用パターン**: IT資格学習だけでなく、トリビアクイズ・謎解き・脱出ゲーム・ゲーム内チュートリアルに転用する。

**12キースキーマのゲーム用マッピング**:

```javascript
{
  "id": "stage-3-puzzle-07",
  "category": "古代文明の謎",               // ゲームのステージ/ジャンル名
  "text": "エジプトのファラオが建設した最大のピラミッドは？",  // 問題文（クイズ/謎）
  "type": "choice",                         // choice = 選択肢型 / text = フリー入力型
  "answer": "A. ギザの大ピラミッド（クフ王）",    // 正解（選択肢と完全一致必須）
  "options": [
    "A. ギザの大ピラミッド（クフ王）",
    "B. カフラー王のピラミッド",
    "C. スネフェル王の赤いピラミッド",
    "D. サッカラの階段ピラミッド（ジェセル王）"
  ],
  "logic": "ギザの大ピラミッド（クフ王、紀元前2560年頃完成）は高さ138.8mで現存最大。...",
                                            // ゲームの「ロア・解説テキスト」として機能
  "plan": "第2章「ファラオの時代」を読んで古王国朝の年表を確認しよう。",
                                            // 不正解時の「ヒントや次のステップ」
  "weight": 0.15,                           // スコア配点（ゲームのXP・得点倍率）
  "textbook_ref": ["chapter-ancient-egypt", "pyramid-builders"],
                                            // ゲーム内の「攻略チャプターID」
  "tags": ["世界史", "建築", "古代エジプト", "中ボス級"],
  "difficulty": "Medium"                    // ゲームレベル（Easy=チュートリアル, Hard=ボス）
}
```

**ゲームシステム固有の追加設計**:
- `weight`をスコア倍率として活用（`Hard`問題は`weight 0.3`で高得点）
- `plan`フィールドを「ヒントボタン押下時のテキスト」として転用（コスト制：1ヒント=10ゴールド）
- `logic`フィールドをクリア後の「ロア解放テキスト」として活用（正解してはじめて全文表示）
- `tags`の「中ボス級」「最終問題」等のゲーム固有タグでUIの演出を制御
- `quality_guard.py`の`logic`密度チェックを「ロアテキストが50文字以上かつ固有名詞3つ以上」に調整

**ゲームタイプ別の転用パターン**:

| ゲームタイプ | `text` | `answer` | `logic` | `plan` |
|---|---|---|---|---|
| トリビア・クイズゲーム | 問題文 | 正解選択肢 | 正解後の解説 | 次の問題ヒント |
| 謎解き・脱出ゲーム | 謎/パズル文 | 解答キーワード | 謎の答えと根拠 | 次のヒント（段階的） |
| ゲーム内チュートリアル | 操作問題文 | 正しい操作 | なぜその操作か | 練習シナリオ |
| RPG知識テスト | 世界観設定の問い | 正しいロア | 世界観の詳細 | 関連クエストID |

**応用要件定義**:
- 「`logic`フィールドはゲームロア（世界観に整合した記述）として機能し、固有名詞・地名・年代のいずれかを3つ以上含むこと」
- 「`difficulty`はゲームステージと連動し、Easy=チュートリアル、Medium=通常ステージ、Hard=ボス戦に対応させること」
- 「`plan`フィールドはヒントシステムとして段階的に開示できるよう、ヒント1/2/3に分割した形式で記述することを推奨する」

**例7: 自己分析・自己評価システム**

**適用パターン**: 性格診断（MBTI風）・強み分析・キャリア適性・スキルギャップ分析・価値観マッピングに転用する。

**根本的な違いと解決策**:
自己分析では「正解がない」ため、`answer`フィールドの意味が変わる。以下のアプローチで対応する。

**解決策A（推奨）**: `answer`を「最頻回答・デフォルト解釈キー」として再定義し、`type`に`"scale"`（新しいLikertスケール型）を追加する。

**解決策B**: `answer`を`null`にして、`quality_guard.py`の「answer in options」チェックをスキップするフラグ(`"type": "analysis"`)を導入する。

**12キースキーマの自己分析用マッピング**:

```javascript
{
  "id": "self-01-openness-07",
  "category": "開放性（Openness）",          // 測定する性格次元・評価軸
  "text": "新しい概念や抽象的なアイデアを考えることに強い魅力を感じる。",
                                            // 自己評価の設問文
  "type": "scale",                          // 新型: Likertスケール（1〜5段階評価）
  "answer": "D. ややあてはまる",             // 最頻回答（統計的最頻値。「正解」ではない）
  "options": [
    "A. 全くあてはまらない",
    "B. あまりあてはまらない",
    "C. どちらともいえない",
    "D. ややあてはまる",
    "E. 非常にあてはまる"
  ],
  "logic": "この設問はBig Five人格理論の「開放性（Openness to Experience）」次元を測定する。"
           "A/Bを選択した場合、具体的・実践的思考を好む傾向（慣例重視型）を示す。"
           "D/Eを選択した場合、抽象的・概念的思考を好む傾向（探求型）を示す。"
           "この次元は職業適性（研究・芸術・哲学系と相性良）に強く相関する（r=0.42）。",
                                            // 各選択肢が示す心理傾向の解釈根拠
  "plan": "開放性が高いあなたには：研究・開発・クリエイティブ職、哲学・文学・芸術の探求、"
          "新しい言語やプログラミングの習得が向いています。",
                                            // スコアに基づく具体的な行動推奨
  "weight": 0.08,                           // この設問の次元への寄与度（重み付けスコア）
  "textbook_ref": ["big-five-model", "openness-dimension"],
                                            // 参照フレームワーク・理論のID
  "tags": ["Big Five", "開放性", "認知スタイル", "職業適性"],
  "difficulty": "Medium"                    // 設問の「深さ」（Mediumは内省が必要なレベル）
}
```

**自己分析システムの設計上のポイント**:

- **スコアリングエンジン**: `weight`×選択肢スコア（A=1〜E=5）の積算で各次元スコアを計算。`factory.py`がディメンション別の集計ロジックを生成する。
- **プロファイル生成**: SQLiteに回答を保存し、`quality_reporter.py`の出力を「あなたのプロファイルレポート」として転用。
- **longitudinal tracking（経時変化追跡）**: 複数回実施した回答データをSQLite + `analytics_schema.sql`で管理し、自分の変化を可視化できる。
- **品質ゲートの転用**: `hallucination_detector.py`の「logic内にanswerのキーワードが含まれるか」チェックを「設問解釈ロジックが選択肢の意味を説明しているか」の確認として転用。
- **`quality_guard.py`の調整**: logicフィールドに「心理学的根拠」（r値・研究名・理論名）が含まれるかチェックするよう変更する。

**自己分析タイプ別の転用パターン**:

| 診断タイプ | `category` | `logic`の内容 | `plan`の内容 |
|---|---|---|---|
| 性格診断（Big Five風） | 性格次元名 | 各選択肢が示す心理傾向 | その性格に向いたライフスタイル |
| 強み分析（StrengthsFinder風） | 資質クラスター | その回答が示す強みの根拠 | 強みを活かすシナリオ |
| キャリア適性 | 職業領域 | 適性の統計的根拠・職種例 | 具体的な職種・学習ロードマップ |
| スキルギャップ | スキル領域 | 現在レベルの判断根拠 | 次に習得すべきスキルと教材 |
| 価値観マッピング | 価値観軸 | 価値観が示すライフ優先度 | 価値観に沿った意思決定フレーム |

**応用要件定義**:
- 「`type`フィールドは既存の`choice`/`text`に加えて`scale`（Likert 1〜5段階）と`ranking`（優先順位付け）を許可する」
- 「`logic`フィールドは各選択肢が示す心理的・行動的傾向を必ず記述し、参照理論名または統計的根拠（r値・出典）を含むこと」
- 「`answer`フィールドは自己分析においては「最頻値」または「中間回答」を格納し、「正解」として扱ってはならない。`quality_guard.py`の`answer in options`チェックは維持する（整合性確認のため）」
- 「回答データは`analytics_schema.sql`の拡張スキーマでユーザーIDと実施日時とともにSQLiteに保存し、経時変化の追跡を可能にすること」
