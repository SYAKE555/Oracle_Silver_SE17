第8章の学習目的

第8章は、1本のSELECTで表現しにくい条件を段階評価で記述する章である。例えば「部署平均以上の社員」「未注文明細の顧客」「存在判定」などは副問合せが有効である。試験では単一行/複数行の演算子選択、相関副問合せの評価順、NOT INとNULLの落とし穴が頻出となる。実務では副問合せの可読性と性能のバランス判断が重要で、場面によってJOINへ書換えるべきこともある。第8章の到達点は、副問合せが返す行数を事前に予測し、適切な比較演算子を選べる状態にすることである。

重要: 副問合せは「ネスト」ではなく「段階評価」。返る行数を読めないSQLは危険。

8.1 副問合せの定義と分類

副問合せはSQL文の内部に入れ子で記述されたSELECTである。戻り行数により単一行副問合せと複数行副問合せに分かれ、外側SQLとの依存有無で非相関と相関に分かれる。定義上の要点は、外側SQLが期待する値の形（1値か複数値か）と副問合せの実際の返却形を一致させることだ。これが一致しないと実行時エラーまたは論理誤りになる。副問合せは万能ではないが、段階的条件表現を明確にできる強力な道具である。

8.2 単一行副問合せ

単一行副問合せは1行1値を返し、`=`、`>`、`<`など単一値比較演算子と組み合わせる。典型例は「全体平均以上」「最大値と一致」などである。試験では単一行比較に複数行が返る誤り（ORA-01427）が頻出。実務では副問合せの結果が本当に単一になるかを先に単体実行して確認するのが安全である。単一前提が揺らぐならINやANY/ALLへ切替えるべきである。

SELECT employee_id, salary
FROM employees
WHERE salary > (
  SELECT AVG(salary)
  FROM employees
);

8.3 複数行副問合せ（IN/ANY/ALL）

複数行副問合せには`IN`、`ANY`、`ALL`を使う。INは集合内いずれか一致、ANYは比較演算と組み合わせて「いずれかに対して成立」、ALLは「すべてに対して成立」を意味する。試験では演算子意味の取り違えが定番。実務では副問合せ結果の重複やNULL混在で挙動が変わるため、事前検証が必須である。単一行比較演算子と混用しないことが基本ルールとなる。

8.4 EXISTS / NOT EXISTS

EXISTSは副問合せに1行でも存在すればTRUEとなる存在判定で、列値より「存在そのもの」を評価する。NOT EXISTSはその否定で、欠損検出に強い。NOT IN + NULL問題を避ける代替として実務で多用される。試験でもEXISTSの意味は頻出で、返却列内容より存在行の有無だけを見ている点が急所である。実務では参照整合の検証や未処理データ抽出に有効である。

8.5 相関副問合せ

相関副問合せは外側SQLの各行値を内側SQLで参照し、行ごとに再評価される。例として「同部署平均以上の社員抽出」がある。非相関より表現力は高いが、行ごと評価のため性能に注意が必要である。試験では評価順を問う設問が多く、内側が外側列を参照する構造を見抜けるかが鍵になる。実務では必要に応じてJOIN+集約へ書換え、実行計画を比較することが推奨される。

SELECT e.employee_id
FROM employees e
WHERE e.salary > (
  SELECT AVG(i.salary)
  FROM employees i
  WHERE i.department_id = e.department_id
);

8.6 副問合せの配置（WHERE/FROM/SELECT）

副問合せはWHERE句以外にもFROM句（インラインビュー）やSELECT句（スカラー副問合せ）で使える。配置場所により責務が変わる。WHERE配置は抽出条件、FROM配置は中間集合構築、SELECT配置は列値導出に向く。試験では配置と挙動の対応が問われる。実務では可読性と性能観点から、最も意図が伝わる配置を選ぶべきである。

8.7 NOT IN + NULL の罠

NOT INの副問合せ結果にNULLが含まれると、条件全体がUNKNOWN化し、期待外れの0件になりやすい。これは試験と実務で最重要の罠の一つである。回避策は副問合せでNULL除去を明示するか、NOT EXISTSへ置換すること。NULLを含む可能性がある集合には、原則としてNOT INを直接使わない運用が安全である。

要注意: NOT INを使う前に副問合せ結果のNULL有無を必ず確認する。

8.8 典型エラー（ORA-01427等）

ORA-01427: 単一行比較に複数行副問合せ。修正はIN/ANY/ALLへの変更か副問合せ単一化。
論理エラー: NOT IN + NULLで0件化。修正はNULL除去またはNOT EXISTS化。
性能劣化: 相関副問合せを無検証で多用。修正はJOIN書換え比較。

8.9 JOINへの書換え判断

副問合せは可読性が高い一方、相関評価でコストが増える場合がある。大量データではJOIN+GROUP BYへ書換えたほうが計画が安定することが多い。逆に存在判定だけならEXISTSの方が意図が明確な場合もある。重要なのは「どちらが速いか」ではなく、要件に対し説明可能で再現性が高い構文を選ぶことだ。実務では実行計画と件数結果を比較して判断するのが定石である。

8.10 実務設計パターン

実務では、副問合せ単体を先に実行して返却行数を確認し、その後に外側SQLへ組み込む手順が有効である。さらに、副問合せ結果のNULL有無確認、演算子妥当性確認、実行計画確認をセットで実施すると事故を減らせる。副問合せは「書ける」より「検証できる」ことが価値であり、検証手順を省略すると障害時の切り分けが困難になる。

品質強化：第8章 超深掘り5項目

1. 定義

第8章の中心概念である「副問合せ」は、単に構文を覚える学習単位ではなく、データの意味・一貫性・運用可能性を同時に成立させるための設計原則である。試験では語句の暗記だけで解ける問題もあるが、実務では入力値の品質、実行順序、例外時の復旧可能性まで含めて定義を扱う必要がある。つまりこの章の定義は「SQL文の形」ではなく「業務データを破壊せずに価値へ変換する規律」であり、ここを誤解すると正解できても現場で再現できない。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。

2. 役割

副問合せの役割は、データベース操作を偶発的な職人技から、再現可能な標準手順へ引き上げることにある。たとえば現場で引継ぎ担当が変わっても、同じ確認SQL・同じ判定基準・同じ実行順で処理できる状態を作るのがこの章の本質である。試験対策の観点でも、役割を理解していると「どの句がどの責務を持つか」を軸に消去法が機能し、難問での正答率が上がる。役割を文法の説明に矮小化せず、品質保証の仕組みとして把握することが重要である。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。

3. 動作原理

副問合せの動作原理は、入力条件の解釈、実行計画に基づく処理、結果または副作用の確定という三層で説明できる。SQLは記述順と論理評価順が一致しない場面が多く、特に結合・集計・更新系では前提条件を誤ると意図外結果になる。そこで原理理解では「どの時点で行が絞られ、どの時点で列が計算され、どの時点で変更が確定するか」を言語化する必要がある。試験ではこの順序差を突く設問が頻出であり、実務ではこの順序差が障害の直接原因になるため、原理を図として説明できるレベルまで落とし込むべきである。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。

4. 制限事項とアンチパターン

副問合せの制限事項を無視したアンチパターンとして、確認なし本実行、条件式の曖昧化、暗黙変換依存、復旧手順未設計がある。これらは短期的には作業を速く見せるが、中長期では誤更新や性能劣化、監査不適合に直結する。特に初学者は「動いたSQL」を正解と誤認しやすいが、品質上は「再実行可能」「失敗時に戻せる」「根拠を説明できる」ことが必須である。制限事項は足かせではなく安全柵であり、これを仕様として受け入れることが事故率低減の最短経路になる。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。

5. 試験・実務の急所

第8章の急所は、見た目が似た構文の意味差を判定できるかどうかである。試験では語順や句の位置、NULLや型変換、更新可否、暗黙コミットなどの境界条件が典型的なひっかけになる。実務では同じ境界条件が本番障害の発火点になるため、各処理に対して「想定件数」「失敗時挙動」「証跡」を先に決める運用が有効である。したがって急所対策は問題演習の量より、誤答理由を分類して再発防止ルールに変換する学習が効果的であり、これを章末の確認手順に固定することで合格後も通用する実力になる。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。
