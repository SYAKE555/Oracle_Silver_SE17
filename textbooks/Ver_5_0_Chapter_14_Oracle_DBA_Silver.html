本ファイルは第14章「ユーザーアクセス制御（権限・ロール）」に集中し、安全な権限設計と運用統制を高密度で解説する。

第14章の学習目的

第14章は、誰に何を許可するかを制御する認可設計を扱う。SQLが正しくても権限設計が甘いと、情報漏えい、誤更新、監査指摘につながる。試験ではシステム権限とオブジェクト権限の違い、GRANT/REVOKE構文、ロールの役割が頻出である。実務では「最小権限」「職務分離」「権限棚卸し」が柱になり、開発都合で広い権限を配ると後で回収不能になる。到達点は、利用者ごとに必要最小限の権限を設計し、運用手順として継続的に維持できる状態にすることである。

重要: 権限管理は一度付与して終わりではない。付与・見直し・剥奪まで含めて設計する。

14.1 認可の基本概念

認可は「認証済みユーザーにどの操作を許可するか」を決める仕組みである。Oracleではユーザー、権限、ロールの3層で管理する。権限は直接付与も可能だが、実務ではロール経由で束ねることで運用負荷を下げる。試験では認証と認可の違いを混同させる問題が出るため、概念分離が必須である。アクセス制御の目的は単なる制限ではなく、業務継続と監査適合の両立である。必要以上に厳しくして業務停止させるのも、広く許可して事故を起こすのもどちらも失敗である。

14.2 システム権限とオブジェクト権限

システム権限はDB全体操作に関わる権限（例: `CREATE SESSION`, `CREATE TABLE`）で、オブジェクト権限は特定表やビューに対する操作権限（例: `SELECT`, `INSERT`）である。試験ではこの分類を問う問題が定番である。実務では、開発者には必要最小限のシステム権限のみ、業務ユーザーには対象表限定のオブジェクト権限を与えるのが基本である。分類を誤ると、個別データ参照だけで済むユーザーに広範囲の作成権限を与えてしまい、統制不備を招く。

14.3 GRANT

GRANTは権限を付与する命令である。`GRANT SELECT ON hr.employees TO app_user;` のように対象を限定して与えるのが原則である。試験ではシステム権限付与とオブジェクト権限付与の構文差、`WITH ADMIN OPTION`や`WITH GRANT OPTION`の意味が問われる。実務では再付与可能オプションを乱用すると権限拡散が起きるため、管理者限定で運用する。付与時には「誰が」「何の業務理由で」「いつまで」を記録し、期限付き運用へつなげるのが望ましい。

GRANT CREATE SESSION TO analyst_user;
GRANT SELECT, INSERT ON sales.orders TO app_writer;

14.4 REVOKE

REVOKEは付与済み権限を剥奪する命令である。運用で見落とされがちだが、異動・退職・役割変更時に即時回収できるかがセキュリティ品質を左右する。試験ではGRANTと対で構文理解が問われる。実務では剥奪による業務影響があるため、事前にアクセス実績と依存処理を確認し、必要なら段階的に回収する。付与だけ増えて剥奪が運用されない環境は、長期的に過剰権限の温床になり、監査で高確率で指摘される。

REVOKE INSERT ON sales.orders FROM app_writer;
REVOKE CREATE TABLE FROM analyst_user;

14.5 ロールの定義

ロールは複数権限をまとめた論理グループであり、ユーザーへ一括適用するための仕組みである。試験ではロール作成、権限付与、ユーザー付与の順序が問われやすい。実務では職務単位でロールを定義し、個別ユーザーへの直接付与を最小化することで管理性を確保する。ロールがない環境では、数百ユーザーへ個別権限を配る運用になり、変更時に漏れが発生しやすい。ロールは可読性の高い命名（`ROLE_REPORT_VIEWER` など）で責務を明確化することが重要である。

CREATE ROLE role_report_viewer;
GRANT SELECT ON sales.monthly_report TO role_report_viewer;
GRANT role_report_viewer TO bi_user;

14.6 ロール設計と最小権限

最小権限原則は「業務遂行に必要な最小限のみ許可する」考え方である。実務では閲覧専用、入力担当、運用管理など職務ごとにロールを分離する。試験では原則名そのものは出なくても、過剰権限の不適切性を問う設問が出る。設計時は「普段使わない強権限を含めない」「一時権限は期限管理」「定期棚卸しで不要権限を回収」の3点が有効である。権限は増やすより減らす方が難しいため、初期設計で保守しやすい粒度に分割することが長期運用を安定させる。

注意: 便利だからと `DBA` 相当権限を配る運用は、最終的に回収不能になりやすい。

14.7 辞書ビューで確認

権限状態は辞書ビューで確認する。ユーザーのシステム権限は`USER_SYS_PRIVS`/`DBA_SYS_PRIVS`、オブジェクト権限は`USER_TAB_PRIVS`/`DBA_TAB_PRIVS`、ロールは`USER_ROLE_PRIVS`/`DBA_ROLE_PRIVS`で追跡できる。試験ではビュー名と確認対象の対応が問われる。実務では権限変更後に差分確認SQLを実行し、申請内容と実体が一致するかを検証する。監査対応では「設定してあるはず」では通らないため、辞書ビュー出力を証跡として保管することが重要である。

SELECT granted_role, admin_option, default_role
FROM user_role_privs
ORDER BY granted_role;

14.8 典型エラーと修正

失敗1: 直接権限の乱発。修正: ロール経由付与へ集約。
失敗2: ADMIN/GRANT OPTIONの過剰付与。修正: 管理者限定で厳格化。
失敗3: 剥奪運用なし。修正: 異動・退職イベントでREVOKEを標準化。
失敗4: 権限変更後の確認省略。修正: 辞書ビュー差分確認を必須化。

14.9 実務運用パターン

推奨運用は「申請→レビュー→GRANT/REVOKE実行→辞書確認→証跡保管→定期棚卸し」である。特にロール中心運用へ統一すると、担当変更時にユーザーをロールへ出し入れするだけで権限管理できる。試験対策ではGRANT/REVOKE構文暗記に加え、権限分類とロール化の意図を説明できるようにする。第14章の本質は、技術的正しさだけでなく統制可能な運用プロセスを設計する点にある。

品質強化：第14章 超深掘り5項目

1. 定義

第14章の中心概念である「ユーザーアクセス制御」は、単に構文を覚える学習単位ではなく、データの意味・一貫性・運用可能性を同時に成立させるための設計原則である。試験では語句の暗記だけで解ける問題もあるが、実務では入力値の品質、実行順序、例外時の復旧可能性まで含めて定義を扱う必要がある。つまりこの章の定義は「SQL文の形」ではなく「業務データを破壊せずに価値へ変換する規律」であり、ここを誤解すると正解できても現場で再現できない。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。

2. 役割

ユーザーアクセス制御の役割は、データベース操作を偶発的な職人技から、再現可能な標準手順へ引き上げることにある。たとえば現場で引継ぎ担当が変わっても、同じ確認SQL・同じ判定基準・同じ実行順で処理できる状態を作るのがこの章の本質である。試験対策の観点でも、役割を理解していると「どの句がどの責務を持つか」を軸に消去法が機能し、難問での正答率が上がる。役割を文法の説明に矮小化せず、品質保証の仕組みとして把握することが重要である。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。

3. 動作原理

ユーザーアクセス制御の動作原理は、入力条件の解釈、実行計画に基づく処理、結果または副作用の確定という三層で説明できる。SQLは記述順と論理評価順が一致しない場面が多く、特に結合・集計・更新系では前提条件を誤ると意図外結果になる。そこで原理理解では「どの時点で行が絞られ、どの時点で列が計算され、どの時点で変更が確定するか」を言語化する必要がある。試験ではこの順序差を突く設問が頻出であり、実務ではこの順序差が障害の直接原因になるため、原理を図として説明できるレベルまで落とし込むべきである。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。

4. 制限事項とアンチパターン

ユーザーアクセス制御の制限事項を無視したアンチパターンとして、確認なし本実行、条件式の曖昧化、暗黙変換依存、復旧手順未設計がある。これらは短期的には作業を速く見せるが、中長期では誤更新や性能劣化、監査不適合に直結する。特に初学者は「動いたSQL」を正解と誤認しやすいが、品質上は「再実行可能」「失敗時に戻せる」「根拠を説明できる」ことが必須である。制限事項は足かせではなく安全柵であり、これを仕様として受け入れることが事故率低減の最短経路になる。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。

5. 試験・実務の急所

第14章の急所は、見た目が似た構文の意味差を判定できるかどうかである。試験では語順や句の位置、NULLや型変換、更新可否、暗黙コミットなどの境界条件が典型的なひっかけになる。実務では同じ境界条件が本番障害の発火点になるため、各処理に対して「想定件数」「失敗時挙動」「証跡」を先に決める運用が有効である。したがって急所対策は問題演習の量より、誤答理由を分類して再発防止ルールに変換する学習が効果的であり、これを章末の確認手順に固定することで合格後も通用する実力になる。 さらに、設計レビュー時には前提条件・入力境界・例外時挙動・確認SQL・証跡項目を明示し、実行者依存の判断を排除すること。学習段階でも、同一テーマを正常系と異常系の両方で検証し、なぜその結果になるかを言語化して再利用可能な知識へ変換する。
