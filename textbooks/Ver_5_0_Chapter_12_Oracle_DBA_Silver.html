第12章の学習目的

第12章では、表を直接公開せずに必要列・必要行だけを提供するビューを扱う。
ビューは見た目上は表に近いが、実体データを持たない論理的オブジェクトであり、SELECT文を名前付きで再利用する仕組みである。
試験では「単純ビューは更新可能になり得る」「集合関数やGROUP BYを含む複雑ビューは更新制約が強い」「WITH CHECK OPTIONとWITH READ ONLYの違い」が頻出である。
実務ではセキュリティ境界、アプリ向け抽象化、SQL再利用性向上に効果が大きい。
到達点は、どの場面でビューを使うべきか、どの条件で更新不可になるかを説明できることである。

重要: ビューは便利だが、基表変更の影響を受けるため依存管理を怠ると障害化する。

12.1 ビューの定義と役割

ビューは「SELECT文に名前を付けた仮想表」である。
役割は主に3つあり、第一に複雑な結合や条件を隠蔽して利用者のSQLを簡素化すること、第二に列・行を制限して不要情報の露出を防ぐこと、第三にロジックを共通化して仕様変更時の修正箇所を減らすことである。
試験では「ビューはデータを保持しない」が基本で、実務では「どの層で責務を持たせるか」が設計の急所になる。
業務で使う際は、ビュー定義をAPI契約として扱い、後方互換を意識して変更することが重要である。

12.2 CREATE VIEW

CREATE VIEWはビュー定義を作成する命令である。
列エイリアスを明示すると、利用側の可読性が上がり、後続の帳票・BI利用が安定する。
試験では構文順序、列名指定、`OR REPLACE`の挙動が問われやすい。
実務では基表の列名をそのまま出さず、ドメイン語彙へ置き換えることで仕様理解が進む。
一方、SELECT * を使うと基表列追加時に意図しない露出が起きるため、列は明示が原則である。

CREATE VIEW v_active_employees AS
SELECT employee_id, last_name, department_id, salary
FROM employees
WHERE status = 'ACTIVE';

12.3 単純ビューと複雑ビュー

単純ビューは原則として1表ベースで、集合関数・GROUP BY・DISTINCTなどを含まない。
条件次第でDML可能になる。
一方、複雑ビューは複数表結合、集計、集合演算を含み、更新制約が強くなる。
試験では「どの定義なら更新可能か」を判定させる問題が多い。
実務では読み取り専用の分析ビューと、更新を許可する業務入力ビューを分離するのが安全である。
用途を混在させると、運用時に権限設計が破綻しやすい。

12.4 ビュー経由DMLの可否

ビュー経由のINSERT/UPDATE/DELETEは、定義内容に依存して可能または不可となる。
単純ビューでも、必須列が露出していない、計算列を含む、キー保全性が崩れる場合は失敗する。
試験では「更新不可要因の識別」が得点ポイントである。
実務では更新用途ビューを設計する場合、必須列露出・制約整合・業務制約を先に確認する。
エラー発生後に調整するのではなく、ビュー定義時に更新シナリオを検証しておくことが重要である。

注意: 「ビュー=常に更新不可」でも「単純ビュー=常に更新可」でもない。
条件判定が必要。

12.5 WITH CHECK OPTION

`WITH CHECK OPTION`は、ビュー定義の条件を満たす行だけ更新/挿入を許可する。
例えば「部署50のみを表示するビュー」で部署60へ変更しようとすると拒否される。
試験では「更新後もビュー条件を満たす必要がある」という意味理解が重要である。
実務では業務境界の逸脱防止に有効で、担当部門以外のデータ改変を防げる。
アプリ側バリデーションだけに依存せず、DB層で強制することで監査適合性も高まる。

CREATE OR REPLACE VIEW v_dept50 AS
SELECT employee_id, last_name, department_id, salary
FROM employees
WHERE department_id = 50
WITH CHECK OPTION;

12.6 WITH READ ONLY

`WITH READ ONLY`はビュー経由DMLを全面禁止し、参照専用窓口として固定する。
分析・配布用途では更新意図がないため、誤更新防止に有効である。
試験ではCHECK OPTIONとの違いを問う比較問題が多い。
CHECK OPTIONは条件内更新を許すが、READ ONLYは一切許さない。
実務では権限管理と組み合わせて「参照は許可、更新は基表の管理者のみ」という分離を実現できる。
運用事故の多くは「更新できる必要がない場所で更新できる」ことから起きるため、READ ONLYは安価で強い対策である。

12.7 OR REPLACEとDROP VIEW

`CREATE OR REPLACE VIEW`は既存ビュー定義を置換する。
再作成に比べて権限再付与漏れを抑えやすいが、列仕様変更は依存オブジェクトへ影響するため注意が必要である。
`DROP VIEW`は定義削除であり、利用中SQLやアプリが即時失敗しうる。
試験ではOR REPLACEの意味、DROPの影響範囲が狙われる。
実務では依存調査（パッケージ、レポート、ETL）を先に実施し、段階リリースで置換するのが安全である。

12.8 辞書ビューで確認

ビュー管理では辞書ビュー確認が必須である。
`USER_VIEWS`で定義SQL、`USER_TAB_COLUMNS`で公開列、`USER_UPDATABLE_COLUMNS`で更新可能列を確認できる。
試験ではどの辞書ビューを使うかを問う問題があるため、目的別に覚える。
実務では定義変更後に「想定列が公開されているか」「更新可否が意図通りか」を検証し、手順書へ記録する。
ビューは論理層である分、見た目だけで正否判断しにくいので、辞書で客観確認する習慣が品質を支える。

SELECT column_name, updatable
FROM user_updatable_columns
WHERE table_name = 'V_ACTIVE_EMPLOYEES'
ORDER BY column_name;

12.9 典型エラーと修正

失敗1: SELECT * でビュー作成し列増加で情報露出。修正: 公開列を明示する。
失敗2: 更新不可ビューでDML実行。修正: 定義要因を確認し用途別に分離。
失敗3: OR REPLACE時に依存影響未調査。修正: 依存オブジェクト一覧を事前確認。
失敗4: READ ONLYを付けず誤更新。修正: 参照専用ビューは明示的に固定。

12.10 実務運用パターン

実務で推奨されるのは、用途別にビュー層を分割する方式である。
外部公開・帳票向けはREAD ONLY、業務更新向けは単純ビュー＋CHECK OPTION、内部分析向けは複雑ビューとし、責務を混ぜない。
これにより権限設計が単純化し、事故時切り分けも容易になる。
試験対策としては、更新可能性の判定軸を言語化して覚えると応用問題にも対応できる。
ビューは単なる省略記法ではなく、データ提供契約を設計する手段として扱うべきである。
