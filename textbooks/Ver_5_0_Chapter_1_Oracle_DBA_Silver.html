第1章の学習目的

第1章は、後続のSELECT、JOIN、副問合せ、DML/DDLを理解するための地盤である。主キー、外部キー、NULL、整合性、SQL分類を曖昧にしたまま先へ進むと、SQL文を暗記しても不具合の原因追跡ができず、実務での改修判断が止まる。逆に第1章を深く理解すると、未知のSQLでも「どの表を基準にし、どの制約を壊し得るか」を論理的に判定できる。試験対策としても、単語暗記ではなく概念間の因果関係を押さえることが重要である。

重要: 第1章は知識の章ではなく判断軸の章。ここで作る判断軸が、障害対応速度と設計品質を左右する。

1.1 RDBの定義と役割

1) 定義（300文字以上）

リレーショナル・データベース（RDB）は、データを行と列の表として管理し、表同士の関係をキーで定義して整合性を保つ仕組みである。単なるファイル保存と異なり、RDBは重複入力防止、参照不能な孤立データ防止、同時更新時の矛盾抑止などの運用上の約束を、制約とトランザクションにより実装する。OracleはこのRDBモデルを基盤に、同時実行制御、障害回復、データ一貫性の維持を実現する。RDBは保管庫ではなく、品質規約を強制できる実行環境であるという理解が重要である。

2) 役割（300文字以上）

RDBの役割を業務で例えると、巨大な在庫倉庫の公式台帳である。棚番号と入出庫履歴が正確なら、現場は商品を迷わず追跡できる。逆に台帳が自由記述だと、同一商品が別名で重複し、在庫差異や誤出荷が増える。顧客、注文、請求のデータでも同じで、RDBは顧客IDや注文IDを軸に事実を分割管理し、必要時にJOINで再構成する。CSVやスプレッドシート主体の運用ではこの関係保証が弱く、表記ゆれと更新漏れが高頻度で起きる。RDBはこうした事故を構造的に減らす基盤である。

3) 動作原理（300文字以上）

RDBの原理は、正規化された表をキーで関連付ける点にある。顧客表に顧客属性、注文表に注文事実と顧客IDを置き、重複保存を減らす。参照時はJOINで必要列を再構築する。主キーは一意性を保証し、外部キーは参照先存在を保証する。更新時はトランザクション境界で扱われ、COMMITまで確定しない。途中失敗時はROLLBACKで整合状態へ戻せる。これにより、書き込み中断や並行更新があってもデータの一貫性を保ちやすい。RDBは「保存」よりも「正しい保存を継続する仕組み」に価値がある。

4) 制限事項とアンチパターン（300文字以上）

制限を軽視した設計は初期稼働できても運用で破綻する。典型は主キー未定義、または変更され得る自然値を主キーにする設計である。主キーが揺らぐと関連外部キーが連鎖破壊し、履歴追跡が困難になる。外部キーを張らずアプリ側のみで整合性を担保する方式も、バッチや手動更新で孤児データを生みやすい。NULLを0や空文字と混同すると集計が歪む。RDB制約は開発速度を下げる障害ではなく、長期運用の事故コストを先払いで抑える保険である。制約を外して短期最適化する判断は、将来の高額な技術的負債に直結する。

5) 試験・実務の急所（300文字以上）

試験では「主キーNULL不可」「外部キー参照整合」「NULLは未知値」の3点が高頻度で問われる。実務ではこの3点が設計レビューの最重要確認項目になる。障害時も、どの制約が有効かを確認するだけで原因候補を大幅に絞れる。逆に制約が薄いシステムは、障害解析が推測頼みとなり復旧が遅延する。学習では「どの制約を置くか」だけでなく「置かないと何が壊れるか」をセットで説明できる状態を目標にする。この視点が試験正答率だけでなく、現場での判断速度を上げる。

1.2 表（テーブル）と行・列の意味

1) 定義（300文字以上）

テーブルは同種データを管理する基本単位であり、列は属性定義、行は業務上の1件データを表す。列には型（NUMBER, VARCHAR2, DATE等）と制約（NOT NULL, CHECK等）を定義し、許容値を規定する。行は主キーで識別され、更新や参照の単位になる。重要なのは、テーブルは画面表示フォーマットではなく業務事実の保管構造である点である。表示都合で列を追加し過ぎると正規化が崩れ、重複と更新異常が増える。テーブル設計はSQL文以前に品質を決める工程であり、後段修正より初期設計の精度が重要である。

2) 役割（300文字以上）

テーブルの役割は、再利用可能な最小単位で業務事実を保存することにある。ECなら顧客、注文、明細、支払、配送を分離して保存することで、同一顧客の属性更新を1か所で完了できる。分離しない場合、同じ顧客情報が複数行へ散在し、更新漏れや矛盾を生む。現場ではこの差が保守工数に直結する。試験では正規化目的として問われるが、実務では監査や問合せ対応の精度向上に効く。設計段階で「この列はどの事実に属するか」を明確化することが、後のSQL難易度を下げる最短策となる。

3) 動作原理（300文字以上）

列定義は「受け入れ可能な値の契約」であり、INSERT/UPDATE時に契約違反があればエラーで拒否される。NUMBER列へ非数値、NOT NULL列へNULL、CHECK違反値などは格納されない。読み出し時はSELECTで必要列のみ投影され、WHEREで行が絞られる。つまりテーブルは保存箱ではなく、入出力の境界で検証を行う実行単位である。定義が厳密なほど、アプリ側での防御コードが減り、障害原因の所在も明確になる。テーブル設計の厳格さは、性能以前にデータ品質の安定性を左右する。

4) 制限事項とアンチパターン（300文字以上）

アンチパターンは1表へ顧客、注文、配送を詰め込む巨大フラット設計である。初期開発は速く見えるが、NULL列が増え、同一情報の重複更新が発生し、整合性監査が破綻する。次に全列VARCHAR2化で型規律を捨てる設計は、比較と集計で暗黙変換エラーを誘発する。必須項目にNOT NULLを付けない設計も未入力データ流入の温床となる。テーブルは「後で補正」ではなく「入口で不正を止める」思想で設計する。これが運用障害を未然に防ぐ基本方針である。

5) 試験・実務の急所（300文字以上）

試験では型選択、制約種別、正規化目的の理解が問われる。実務では要件定義時に必須項目をNOT NULLで固定できるかが品質分岐点になる。ログ系でも安易に文字列型を乱用すると、分析要件追加時に変換負債が爆発する。設計レビューでは「この列は将来集計するか」「欠損を許容するか」「識別子として安定か」を列ごとに確認する習慣が有効である。学習段階でこの観点を身につけると、試験合格後に実案件で通用する設計判断へ直結する。

1.3 主キー（Primary Key）

1) 定義（300文字以上）

主キーは表内の各行を一意に識別する列または列組の制約であり、重複とNULLを許容しない。候補キーの中から代表として選ばれ、関連表から参照される基点になる。OracleでPRIMARY KEYを定義すると一意性が保証され、参照整合設計の中核となる。主キーは単なるID列ではなく、更新、削除、履歴追跡、障害調査の共通座標である。主キーが曖昧な表は同一行の特定精度が落ち、誤更新や重複登録を防ぎにくくなる。

2) 役割（300文字以上）

主キーの役割は「長期的にぶれない識別子」を与えることにある。顧客名や電話番号は変更されるため識別子として不安定である。主キーが安定すれば、表示名が変わっても同一主体として追跡できる。運用現場では問合せ対応、監査、復旧で対象行を正確に特定する必要があるため、主キーは実務上の生命線になる。主キー設計を軽視すると、同名異人の判別失敗や履歴混在が起き、誤請求や誤通知など重大事故へつながる。見やすさは表示列で担保し、識別子は不変性で選ぶのが原則である。

3) 動作原理（300文字以上）

INSERT時、Oracleは主キー値の重複有無を検査し、衝突すればエラーで拒否する。NULL値も拒否される。UPDATEで主キー変更を行うと、参照外部キーへの影響が発生するため運用上高コストになる。主キーは一意索引と連動しやすく、検索と結合の基準としても機能する。つまり主キーはラベルではなく、一意性検証、参照安定、アクセス効率の三要素を同時に支える。設計時には「長期不変」「外部連携で衝突しない」「桁ルール変更に耐える」値を採用する必要がある。

4) 制限事項とアンチパターン（300文字以上）

アンチパターンは可変の業務値を主キーにすること。メールアドレスや社員番号運用桁は変更される可能性があり、変更時に関連表を連鎖更新する必要が生じる。複合主キーを無秩序に増やす設計も外部キー定義を複雑化し保守性を落とす。複合キーは業務上一意条件として不可欠な場合のみ採用し、不要なら代理キーとUNIQUE制約の併用が扱いやすい。主キー未定義で開発を進める設計は重複防止機構を失うため、実務では受け入れ不可である。

5) 試験・実務の急所（300文字以上）

試験ではPRIMARY KEYのNULL不可、1表1主キー（列組可）、UNIQUEとの違いが典型出題である。実務では主キー戦略を最初に確定することで、後続表の外部キー設計が安定する。新人が誤りやすいのは「業務上読みやすい値=主キー」という誤解であり、可読性は表示列に分離すべきである。レビューでは「10年後も不変か」「他システム連携で競合しないか」を確認する。主キー設計が固まるとDML運用、データ移行、障害復旧の難易度が大幅に下がる。

CREATE TABLE customers(
  customer_id NUMBER PRIMARY KEY,
  customer_name VARCHAR2(100) NOT NULL
);

1.4 外部キー（Foreign Key）

1) 定義（300文字以上）

外部キーは、子表の値が親表の主キーまたは一意キーに存在することを保証する制約である。これにより参照先不在のデータ登録を防ぎ、表間関係を実行時に強制できる。OracleはINSERT/UPDATE/DELETE時に参照整合性を評価し、違反があればエラーで拒否する。外部キーはER図上の関係を単なる設計書記号で終わらせず、DBで実効性ある規約へ変換する仕組みである。業務データが長期蓄積されるほど、外部キー有無の差は品質格差として顕在化する。

2) 役割（300文字以上）

外部キーの役割は孤児データ防止である。存在しない顧客IDの注文が通ると、請求・配送・問い合わせ処理で参照不能が発生し業務停止を招く。外部キーがあれば登録時点で不整合を拒否でき、障害の拡散を防げる。生活で言えば、存在しない住民番号へ行政手続きを紐づけないのと同じで、制度で整合を守る発想に近い。短期開発で外部キーを省くと初速は出るが、運用で不整合修復コストが増大する。長期運用前提では外部キーは必須の保険である。

3) 動作原理（300文字以上）

子表INSERT/UPDATE時、外部キー値が親表に存在するかをOracleが検査する。存在しなければORA-02291などで失敗する。親行DELETE時は子参照が残るとORA-02292で削除不可となる（ON DELETE CASCADE等を設定しない場合）。同一トランザクションで親子を正しい順序で投入すれば整合は成立する。削除方針はRESTRICT/CASCADE/SET NULL等を要件で選定する。外部キーは単なる紐付け列ではなく、更新順序と削除ルールまで規定する運用制約である。

4) 制限事項とアンチパターン（300文字以上）

アンチパターンは削除ポリシー未定義のまま外部キーを設定すること。運用で親削除要件が発生した際、参照制約エラーで手順停止する。逆に意味を理解せずCASCADEを乱用すると、親1件削除で大量子データが消える事故を引き起こす。性能を理由に外部キーを一律除去する判断も危険で、整合性崩壊リスクをDB外へ押し出すだけである。性能問題は索引や処理設計で解くべきで、制約削除は最終手段。設計段階で「削除時に何を残し何を消すか」を必ず文章化してから制約を定義すること。

5) 試験・実務の急所（300文字以上）

試験では親キー種別、参照整合違反時の挙動、削除時ルールが頻出である。実務では親子投入順序と削除順序を誤るとバッチが停止するため、運用手順書へSQL順序を明示する必要がある。監査では外部キー定義が整合性担保の強い証拠となる。外部キーなしで運用する場合、同等検証をアプリとバッチ双方で再実装する必要があり、漏れが生じやすい。したがって要件上許す限り、整合性はDB制約で担保するのが定石である。

CREATE TABLE orders(
  order_id NUMBER PRIMARY KEY,
  customer_id NUMBER CONSTRAINT orders_customer_fk
    REFERENCES customers(customer_id)
);

1.5 NULLと3値論理

1) 定義（300文字以上）

NULLは0や空文字ではなく、値が未知または未設定である状態を表す。SQL比較はTRUE/FALSEの二値ではなくUNKNOWNを含む3値論理で評価され、NULLを含む比較は通常UNKNOWNになる。したがってNULL判定は等号ではなくIS NULL/IS NOT NULLで行う必要がある。NULL概念が曖昧だと、抽出漏れ、件数不一致、誤集計が連鎖する。Oracle学習では文法より先に、NULLを独立した状態値として扱う理解を固めることが最重要である。

2) 役割（300文字以上）

NULLの役割は未知と既知の区別である。退職日未確定の社員へ0や空文字を入れると、意味的には誤情報になる。NULLなら「未決定」という業務状態を正確に保持できる。実務では未設定件数監査、入力漏れ検知、処理未完了抽出にこの区別が効く。NULLを雑に代替値へ置換すると、未入力が正常値に埋もれて品質問題が見えなくなる。NULLは欠陥ではなく、業務状態を表現する正式なデータ状態であり、扱い方を規約化することが重要である。

3) 動作原理（300文字以上）

WHERE句はTRUE行のみ採用する。NULL比較は多くがUNKNOWNとなるため、salary = NULLは一致しない。IS NULLを使えば明示判定できる。集計ではCOUNT(col)がNULLを除外し、COUNT(*)は行数をそのまま数える。この差は試験と実務の両方で頻出する。数値演算でNULLが混在すると結果がNULL化するため、NVL/COALESCEで代替値補完方針を定める必要がある。3値論理を理解すると、抽出結果を事前予測でき、デバッグ時間を大きく短縮できる。

4) 制限事項とアンチパターン（300文字以上）

代表的アンチパターンは、NULLを等号比較する、NOT INへNULL混在集合を渡す、未入力を0保存する、の3つである。NOT IN + NULLは条件全体がUNKNOWN化し、期待外れの0件を返しやすい。修正はNOT EXISTS活用、または比較集合のNULL除去である。NULL許容を無方針に広げると、業務必須値欠損が増えデータ品質が低下する。NULLは必要な場面だけ許容し、必須項目はNOT NULLで入口遮断する。設計時に「未知を許容する理由」を明記する習慣が有効である。

5) 試験・実務の急所（300文字以上）

試験ではNULL比較、3値論理、COUNT差分が高確率で出題される。実務では帳票件数不一致の原因としてNULL判定誤りが多い。障害調査の初手としてNULL条件と集計関数の使い分けを確認する習慣を持つと復旧が速い。開発規約として「NULL判定はIS NULL明示」「NOT IN使用時はNULL混在検査」「計算前にNVL方針定義」を固定すると事故を減らせる。NULLは難解概念ではなく、規則的に扱えば制御可能である。

SELECT employee_id
FROM employees
WHERE commission_pct IS NULL;

1.6 SQL分類（DQL / DML / DDL / TCL）

1) 定義（300文字以上）

SQLは目的別に分類される。DQLは取得（SELECT）、DMLはデータ変更（INSERT/UPDATE/DELETE/MERGE）、DDLは構造変更（CREATE/ALTER/DROP/TRUNCATE）、TCLはトランザクション制御（COMMIT/ROLLBACK/SAVEPOINT）を担当する。この分類は暗記用ラベルではなく、実行副作用や復旧可否を判断するための運用分類である。DMLはトランザクション境界で戻せるが、DDLは暗黙COMMITが絡み戻しにくい。分類理解は事故防止の前提知識になる。

2) 役割（300文字以上）

分類の役割は作業危険度と承認手順を切り分けることにある。DQLは参照中心で比較的安全だが、DMLは業務データを書き換えるため事前確認が必須、DDLは影響範囲が広く変更管理対象、TCLは確定/取消を制御する。現場で「今のSQLがどの分類か」を意識するだけでレビュー粒度と実行手順を最適化できる。分類を無視すると、更新系SQLを参照感覚で実行する事故が起きる。分類は学習用用語ではなく、運用安全設計の座標軸である。

3) 動作原理（300文字以上）

DQLは結果集合を返しDB状態は変えない。DMLは未確定変更をトランザクションへ蓄積し、COMMITで永続化する。TCLはこの境界を制御する。DDLはデータ辞書を更新し、実行時点で構造を変えるためDMLと同列に扱えない。OracleではDDL前後で暗黙COMMITが発生し得るため、DML混在時に想定外確定が起きる。分類理解は「何が戻せて何が戻せないか」を判断するための実践知識であり、障害時の初動品質に直結する。

4) 制限事項とアンチパターン（300文字以上）

アンチパターンはDML作業中にDDLを混在させること、COMMITタイミングを曖昧にすること、参照SQL感覚で更新SQLを実行することである。障害対応で焦ってDDLを打つと暗黙COMMITにより復旧不能状態を作りやすい。対策は分類ごとの作業分離、更新前件数確認、SAVEPOINT活用、DDL事前影響分析である。分類を運用規約へ落とし込まないと、知識があっても事故防止に結びつかない。チーム共通の実行チェックリスト化が有効である。

5) 試験・実務の急所（300文字以上）

試験では文の分類と作用、特にTRUNCATEの扱いが問われる。TRUNCATEは高速だがDDLであり、DELETEと同じ感覚で使うと復旧設計を誤る。実務レビューでも「このSQLは分類上どこか」「戻せるか」「承認レベルは妥当か」を確認する必要がある。分類を定義暗記で終わらせず、運用判断へ接続できるかが合格後の実務適応力を左右する。分類を軸に作業設計できる人は、障害時の判断が速く一貫する。

1.7 正規化（第1〜第3正規形）

1) 定義（300文字以上）

正規化はデータ重複と更新異常を抑えるために、表構造を論理的に分解する設計手法である。第1正規形は繰り返し属性の排除と原子性確保、第2正規形は部分関数従属の除去、第3正規形は推移的従属の除去を目的とする。重要なのは表数を増やすこと自体ではなく、業務事実の責務を分離し、一貫した更新を可能にする点にある。Oracle学習では用語で出題されるが、実務では障害予防策として機能する。

2) 役割（300文字以上）

正規化の役割は、同じ情報を複数箇所へ保存しないことによる更新漏れ防止である。受注表へ顧客住所を毎回保持すると、住所変更時に多数行更新が必要になり、漏れれば帳票矛盾が発生する。顧客表へ分離し受注表は顧客ID参照にすれば、住所更新は1行で完結し整合性が維持される。現場ではこの差が保守工数と障害率を大きく左右する。正規化は理論演習ではなく、長期運用に耐える構造を作る実践手法である。

3) 動作原理（300文字以上）

正規化ではまず識別子を決め、各属性がその識別子へどう依存するかを確認する。完全従属しない属性は別表へ分離し、外部キーで関連づける。更新時は責務表のみ変更し、参照時はJOINで復元する。この設計により更新異常、挿入異常、削除異常を低減できる。分離後にPK/FK/UNIQUE/NOT NULLを適切配置すると、理論上の分解が実行時整合性として機能する。正規化は保存時に整理し参照時に再構築するRDB原理の具体化である。

4) 制限事項とアンチパターン（300文字以上）

アンチパターンは理論優先で過分割し、JOIN本数を過剰に増やす設計である。可読性低下と性能劣化を招くため、要件に応じた粒度調整が必要となる。逆に非正規化を無方針で進めると重複更新と矛盾を量産する。将来用の不明列を先置きする設計もNULLだらけの曖昧表を生む。分析系では意図的非正規化が有効な場合もあるが、同期元と更新責任を明示しなければ整合性事故になる。正規化は万能ではないが、方針なき非正規化より遥かに安全である。

5) 試験・実務の急所（300文字以上）

試験では部分関数従属と推移的従属の識別がひっかけになる。実務では語義暗記より「この属性を更新する時、何表何行を触るか」で設計品質を判定できる。説明できない構造はほぼ設計不備を含む。さらに正規化後に外部キーを張らないと、理論上正しくても実データが崩れる。学習時は受注、顧客、商品、明細を題材に、どこを分離し何の制約で守るかを自分で説明できる状態を目標にする。これが試験対策と実務耐性の共通基盤となる。

1.8 Oracleアーキテクチャ最小理解（インスタンスとデータベース）

1) 定義（300文字以上）

Oracleではインスタンスとデータベースを分けて理解する。インスタンスはSGAとバックグラウンドプロセスで構成され、SQL実行とI/O制御を担当する。データベースはデータファイル、制御ファイル、REDOログファイル等の物理ファイル集合で、永続データを保持する。試験ではこの区別が頻出であり、実務でも障害切り分けの起点となる。第1章では詳細パラメータ暗記より、処理主体と保存主体が別であるという境界理解を最優先で押さえるべきである。

2) 役割（300文字以上）

役割を工場で例えると、インスタンスは稼働設備、データベースファイルは完成品倉庫である。設備停止なら処理が止まり、倉庫破損なら在庫を失う。問題がどちらかで復旧手順は変わる。接続不能時に全てファイル破損と決めつけると不要作業が増えるし、逆に物理破損を再起動だけで解決しようとして悪化させることもある。SQL学習者でもこの切り分け感覚を持つと、障害時の調査観点が整理され、無駄な再実行を減らせる。

3) 動作原理（300文字以上）

SQL実行時、インスタンス側でパース、最適化、ブロック読込が行われ、変更はまずメモリ側で管理される。DMLはUNDO/REDO情報とともに処理され、バックグラウンドプロセスにより段階的に永続化される。COMMITは変更結果の確定点であり、障害時はREDOを使って一貫性復旧を行う。これにより性能と耐障害性が両立する。第1章で「SQL実行=即データファイル直書き」ではない点を理解しておくと、後続章のトランザクション理解が大幅に容易になる。

4) 制限事項とアンチパターン（300文字以上）

アンチパターンは概念混同による誤対応である。接続障害を常にデータ破損扱いする、あるいはファイル異常を単純再起動で済ませる判断は復旧遅延を招く。さらにCOMMIT設計を軽視し無境界の大量更新を行うと、UNDO圧迫や競合増加で性能障害を引き起こす。学習段階で処理主体と保存主体の境界を固定し、観測事実に基づく切り分けを徹底することが重要である。闇雲な再実行より、構造理解にもとづく原因分解が事故を減らす。

5) 試験・実務の急所（300文字以上）

試験ではインスタンス構成、物理ファイル構成、REDO/UNDOの役割が問われる。実務では性能問題と破損問題で見るべき指標が異なるため、入口判断を誤ると復旧が遅れる。例えば更新遅延は実行計画やI/O待機を優先調査し、即座に物理破損扱いしない。第1章でこの判断軸を持つと、以降のSQL学習が文法暗記で終わらず「なぜそのSQLがその挙動になるか」の理解へつながる。合格後の現場適応力を高める土台となる。

1.9 制約の比較整理（NOT NULL / UNIQUE / PK / FK / CHECK）

1) 定義（300文字以上）

制約は列または表に対して許容値と関係性を宣言し、不正データの登録をDBエンジン側で拒否する仕組みである。NOT NULLは欠損禁止、UNIQUEは重複禁止、PRIMARY KEYは一意かつNULL禁止、FOREIGN KEYは参照整合、CHECKは任意条件検証を行う。これらを組み合わせることで、アプリ実装差に依存せず品質を維持できる。試験では個別機能として出るが、実務では業務ルールをデータ仕様へ翻訳する道具一式として扱うことが正しい。

2) 役割（300文字以上）

制約の役割は入力時点で不正を止めることにある。後から検知して修正する運用は、下流へ不整合が拡散し修正コストが急増する。数量負数や存在しない顧客参照を入口で拒否すれば被害は局所化できる。外部キーがなければ参照不能データが静かに蓄積し、後で大量修復が必要になる。制約は開発速度の敵ではなく、運用停止を防ぐ安全装置である。設計レビューで「どの業務ルールをどの制約で担保するか」を明文化することが品質保証の基本となる。

3) 動作原理（300文字以上）

INSERT/UPDATE時にOracleは適用制約を評価し、違反があれば文を失敗させる。主キー/一意制約は索引と連携しやすく、整合性と検索効率を両立する。外部キーは親子関係を照合し、参照先不在や削除矛盾を検出する。CHECKは条件式評価で範囲外値を拒否する。制約は事後監視ではなく事前遮断であるため、違反データを格納させない点が本質である。これにより障害を未然に防ぎ、データ修復の後追いコストを削減できる。

4) 制限事項とアンチパターン（300文字以上）

アンチパターンは性能を理由に制約を無差別に外す判断である。確かに検証コストは発生するが、整合性崩壊の復旧コストに比べれば通常小さい。アプリ側検証のみでDB制約を持たない設計も、バッチや手動更新経路で破綻しやすい。CHECK条件を曖昧にすると正当データ拒否という逆障害も起きる。制約は厳しければ良いのではなく、業務ルールと運用導線を踏まえて定義すべきである。導入時は受入/拒否ケースを事前テストし、運用手順へ反映することが必要である。

5) 試験・実務の急所（300文字以上）

試験ではUNIQUEとPRIMARY KEYの差、外部キー条件、NOT NULL特性が繰り返し問われる。実務では制約名を明示命名しておくと障害解析が速い。自動命名のままだとログで意味が取りづらい。設計規約として「必須列NOT NULL」「候補識別子UNIQUE」「業務コードCHECK」「関連表FK必須」を統一すると品質のばらつきが減る。学習では暗記に加え、各制約がどの事故を防ぐかを具体例で説明できることを目標にする。これが合格後の即戦力化につながる。

1.10 DBタイプ比較と選定観点（学習用整理）

1) 定義（300文字以上）

業務システムで使われるDBにはRDB、キー・バリュー型、ドキュメント型、列指向型などがある。DBA Silverの主対象はRDBであり、整合性制約、SQL問い合わせ、トランザクション制御を重視する。ここで重要なのは他方式の優劣ではなく、試験範囲がRDB中心である理由を理解することだ。RDBは厳密整合と複雑検索を両立し、監査と長期運用に向く。DB選定は流行ではなく要件適合で判断すべきである。

2) 役割（300文字以上）

比較の役割は道具選定ミスを防ぐことである。会計のような厳密整合が必要な領域でスキーマ管理を緩めると監査要件を満たしにくい。逆に可変構造ログを厳格固定すると開発が重くなる。実務では併用が一般的で、基幹データはRDB、キャッシュや一時セッションは別方式という責務分離を取る。学習者がこの住み分けを理解しておくと、RDBの制約やSQLの厳密さを不便ではなく必要条件として受け止められる。

3) 動作原理（300文字以上）

RDBは定義済みスキーマへ沿って入力を検証し、最適化器が宣言的SQLの実行計画を作る。キー・バリュー型は単純参照高速化に強いが、関係性管理をアプリへ寄せる傾向がある。ドキュメント型は可変構造を持ちやすいが、厳密な関係制約は設計依存となる。列指向は分析系集計に強い。差分は「どこで整合性を担保するか」「検索柔軟性をどこへ置くか」に集約される。第1章ではRDBの規律が基幹運用の安定性につながる点を押さえる。

4) 制限事項とアンチパターン（300文字以上）

アンチパターンは要件分析なしで流行技術を採用すること。監査、復旧、権限制御など非機能要件との不整合が後から顕在化する。逆にRDBへ全責務を詰め込み、キャッシュ用途まで同一基盤で処理して性能劣化を招くケースもある。方式選定は二者択一でなく責務分離設計である。判断軸は「厳密整合が必要か」「結合検索が主要求か」「更新一貫性の優先度は高いか」であり、これらが高い場合はRDB主軸が妥当となる。

5) 試験・実務の急所（300文字以上）

試験はRDB概念理解を前提に制約、SQL、トランザクションを問うため、RDBを選ぶ理由まで説明できることが重要である。実務の技術選定会議でも「なぜOracle/RDBか」を問われる。整合性、監査対応、運用成熟度、既存SQL資産継承の観点で説明できると説得力が高い。第1章でこの判断軸を持つことで、以降の文法学習が目的のある知識に変わる。丸暗記ではなく、要件に応じた技術判断へつなげることが実務力に直結する。
