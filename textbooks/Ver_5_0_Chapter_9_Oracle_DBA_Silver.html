第9章の学習目的

第9章は、複数SELECT結果を集合として統合・比較する章である。
JOINが列結合を担うのに対し、集合演算子は行集合同士を合成する。
試験ではUNIONとUNION ALLの違い、INTERSECT/MINUSの意味、列数と型整合、ORDER BYの配置が高頻度で問われる。
実務では差分抽出、重複排除付き統合、監査比較で多用されるが、型整合ミスや重複除去コスト見落としで障害になりやすい。
第9章の到達点は、要件に応じて適切な演算子を選び、結果件数と性能影響を説明できる状態にすることである。

重要: 集合演算子は「似たSELECTをつなぐ」機能ではない。
結果集合の意味を変える演算そのもの。

9.1 集合演算子の定義

集合演算子は複数のSELECT結果を集合として結合・比較する機能で、UNION、UNION ALL、INTERSECT、MINUSが代表である。
定義上の要点は、各SELECTの列数と型グループが整合していることが前提である点だ。
列名は先頭SELECTに従う。
JOINとの違いは、JOINが横方向（列追加）であるのに対し、集合演算子は縦方向（行集合統合）である。
実務では同種データの統合や差分確認に有効であり、誤用すると重複処理や件数解釈を誤る。

9.2 UNION

UNIONは複数結果を統合し、重複行を除去して返す。
重複除去処理が入るため、件数は単純加算にならない。
試験ではUNION ALLとの差分が頻出。
実務では「重複排除が要件か」を明確にしないと、必要行が消えたように見える誤認が起きる。
重複排除が不要ならUNIONを使う理由は薄く、性能面でも不利になりやすい。

▲ トップへ戻る

9.3 UNION ALL

UNION ALLは重複を除去せず結果を連結する。
件数は通常、各SELECTの合計に近くなる。
重複が業務上意味を持つログ系や監査系ではUNION ALLが自然である。
試験では「性能重視はUNION ALL」が定番。
実務でも重複排除が不要な場面ではまずUNION ALLを選び、必要時のみ別途重複処理を設計する方が明確である。

SELECT employee_id FROM employees WHERE department_id = 10
UNION ALL
SELECT employee_id FROM employees WHERE department_id = 20;

9.4 INTERSECT

INTERSECTは双方のSELECTに共通して存在する行のみ返す。
共通集合抽出に使え、監査突合や一致確認に有効である。
重複は集合として扱われるため結果で整理される。
試験では演算意味の理解が中心。
実務では比較基準列をどこまで含めるかで一致判定が変わるため、列選定を明確にする必要がある。

9.5 MINUS

MINUSは1本目に存在し2本目に存在しない行を返す差分演算である。
欠損抽出や未反映レコード確認に有効。
順序が逆になると意味が反転するため、実務では「何から何を引くか」を明示する必要がある。
試験では演算方向の取り違えがひっかけになる。
差分抽出では列の正規化（前後空白・大文字小文字差）も合わせて検討するべきである。

9.6 列数・型グループ整合

集合演算子の前提は列数一致と型グループ整合である。
1本目NUMBER、2本目VARCHAR2などの不整合はエラー要因になる。
実務ではCASTで型を揃えるのが定石で、書式付き文字列化は最終段で行うべきである。
列順も一致させなければ意味が変わる。
試験ではこの基本仕様が頻出のため、まず「列数」「型」「順序」を機械的に確認する癖をつけることが重要である。

失敗例: 1本目NUMBER、2本目VARCHAR2混在。修正: CASTで型統一。

9.7 ORDER BYの位置と制約

集合演算子を使うSQLでは、ORDER BYは原則として最後に1回だけ適用する。
途中SELECTに個別ORDER BYを置く設計は文法上・意味上の混乱を招きやすい。
試験でもORDER BY位置は定番。
実務では最終結果の並び順だけを定義し、途中並び順への依存を作らない方が保守しやすい。
必要なら各SELECTをサブクエリ化して段階明示する。

9.8 性能観点（重複除去コスト）

UNION、INTERSECT、MINUSは重複整理や比較のために追加処理が入り、データ量が多いとコストが増える。
UNION ALLは比較的軽く、性能優先時に有利である。
実務ではまずUNION ALLで必要件数を確認し、真に重複排除が必要な場面だけUNIONへ切替える方が合理的である。
集合演算子の選択は意味だけでなくコストを含む設計判断である。

9.9 典型エラーと修正

失敗1: 列数不一致。修正: SELECT列数を合わせる。
失敗2: 型グループ不整合。修正: CASTで統一。
失敗3: UNIONで件数が減る理由を説明できない。修正: 重複排除要否を要件化。
失敗4: MINUSの方向を逆に記述。修正: 差分元と差分先を明示。

9.10 実務運用パターン

実務では「まずUNION ALLで生データ確認」「次に必要なら重複除去」「最後にORDER BY」で段階的に組むと検証しやすい。
差分抽出ではMINUS前に正規化（TRIM/UPPER等）を行い、見た目差異での誤差分を避ける。
監査用途では演算前後件数を記録し、結果再現性を担保する運用が有効である。
集合演算子は短く書けるが、検証手順込みで設計することが重要である。

第9章 試験ひっかけパターン集

ひっかけ1: UNION ALLは重複除去するか → しない。
ひっかけ2: MINUSは左右どちらでも同じか → 同じではない。
ひっかけ3: 集合演算子で列名は各SELECTで独立か → 先頭SELECTに従う。
ひっかけ4: ORDER BYは各SELECTに書くか → 最後に1回が基本。
ひっかけ5: 列型不整合でも暗黙で解決されるか → エラーになる場合がある。
