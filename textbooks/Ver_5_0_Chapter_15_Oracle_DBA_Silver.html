第15章の学習目的

第15章では、Oracle内部メタデータを参照するデータ・ディクショナリ・ビューを学ぶ。表や制約、権限、索引、シーケンスの状態を正確に把握するために必須であり、試験でも頻出分野である。実務では「設定したつもり」を排除し、辞書ビューで実体確認することが変更品質を支える。特に障害調査や監査対応では、辞書ビューから客観証拠を取得できるかが重要である。到達点は、目的別に適切な辞書ビューを選び、確認SQLを自力で組み立てられる状態にすることである。

重要: DDL/DCL後の確認を省くと、設計書と本番実体の差異を長期間見逃す。

15.1 データ・ディクショナリの定義

データ・ディクショナリは、Oracleが保持するオブジェクト定義・権限・統計などのメタ情報集合である。利用者は主にビュー経由で参照する。試験では「辞書ビューはDB管理情報を提供する」という基本理解が問われる。実務では、障害時の切り分けで「表は存在するか」「制約状態はどうか」「権限不足か」を即時確認するため、辞書参照能力が作業時間を大きく左右する。アプリデータを見るSQLと、DB状態を見るSQLを分けて考えることが重要である。

15.2 USER_/ALL_/DBA_ の違い

`USER_`は自スキーマ対象、`ALL_`はアクセス可能対象、`DBA_`はDB全体対象を示す。試験ではこの接頭辞の意味差が最重要ポイントである。実務では、権限不足で`DBA_`が見えない場面も多いため、まず`USER_`/`ALL_`で確認し、必要時に管理者へ依頼する運用が現実的である。接頭辞の意味を誤解すると、存在しないと誤判定したり、監査範囲を取り違えたりする。ビュー名暗記だけでなく「どの視点の情報か」を常に意識することが重要である。

SELECT table_name FROM user_tables;
SELECT owner, table_name FROM all_tables WHERE table_name = 'EMPLOYEES';
-- DBA権限がある場合
SELECT owner, table_name FROM dba_tables WHERE table_name = 'EMPLOYEES';

15.3 オブジェクト確認ビュー

代表的な確認対象は表・ビュー・索引・シノニム・シーケンスである。`USER_TABLES`、`USER_VIEWS`、`USER_INDEXES`、`USER_SYNONYMS`、`USER_SEQUENCES`を使い分ける。試験では「どのビューで何が分かるか」を問う選択問題が多い。実務では変更作業後に対象オブジェクトの存在・状態・属性を1セットで確認し、証跡化する。1つのビューだけ見て完了扱いにすると、関連定義の漏れを見逃す可能性が高い。複数ビューを組み合わせて確認する癖が品質を上げる。

15.4 列定義と制約確認ビュー

列定義確認は`USER_TAB_COLUMNS`、制約確認は`USER_CONSTRAINTS`と`USER_CONS_COLUMNS`が基本である。試験では制約種別コード（`P`主キー、`R`外部キー等）の意味が問われる場合がある。実務では「列は追加されたがNOT NULLが有効か」「FKは期待通り有効か」を検証するため、制約状態（ENABLED/DISABLED）まで確認する。DDL実行だけで満足すると、無効制約のまま本番運用に入り品質事故につながる。定義と状態を両方確認するのが実務の基本である。

SELECT constraint_name, constraint_type, status
FROM user_constraints
WHERE table_name = 'PROJECT_TASKS'
ORDER BY constraint_name;

15.5 権限確認ビュー

権限周りは`USER_SYS_PRIVS`、`USER_TAB_PRIVS`、`USER_ROLE_PRIVS`が中心である。試験では「どのビューでシステム権限を見るか」など対応関係の知識が問われる。実務では権限申請対応後に、対象ユーザーへ必要権限が付与済みか、不要権限が残っていないかを確認する。権限エラー対応で手作業推測を続けると復旧が遅れるため、辞書ビューで事実確認する手順を固定化することが有効である。監査対応でもこの出力がそのまま証拠になる。

SELECT privilege FROM user_sys_privs ORDER BY privilege;
SELECT table_name, privilege FROM user_tab_privs ORDER BY table_name, privilege;

15.6 運用監視での活用

辞書ビューは試験対策だけでなく運用監視の中核でもある。例として「無効オブジェクト検知」「期限切れアカウント確認」「不要権限棚卸し」などを定期化できる。実務では日次/週次レポートに辞書SQLを組み込み、差分監視で異常を早期検知する。障害時はまず辞書で状態把握し、次にデータ層へ進む順序が効率的である。辞書ビューを知らないと、問題切り分けが経験依存になり再現性が落ちる。標準SQL化してチームで共有することが重要である。

15.7 典型エラーと修正

失敗1: USER_とALL_の違いを誤解。修正: 参照視点を明確化して使い分け。
失敗2: DDL後に辞書確認なし。修正: 確認SQLを変更手順へ固定。
失敗3: 権限エラーを推測で対応。修正: USER_TAB_PRIVS等で事実確認。
失敗4: 監査証跡未保存。修正: 辞書出力を定期保管。

15.8 実務運用パターン

推奨運用は「変更SQL」と「確認SQL」を常にペア管理し、適用後に辞書ビューで必ず検証する方式である。監査観点では、権限・制約・オブジェクトの定期棚卸しを自動化すると品質が安定する。試験対策としては代表ビュー名を丸暗記するだけでなく、どの業務場面で使うかを紐付けて覚えると定着しやすい。第15章の価値は、DB状態を客観データで説明できるようになる点にある。これは運用現場で最も評価される基礎能力である。

第15章 試験ひっかけパターン集

ひっかけ1: `USER_TABLES`で他スキーマ表を確認できるか → 通常できない。
ひっかけ2: `DBA_`ビューは誰でも参照可能か → いいえ。権限が必要。
ひっかけ3: 制約確認は`USER_TAB_COLUMNS`だけで十分か → 不十分。`USER_CONSTRAINTS`も必要。
ひっかけ4: 辞書ビューは試験専用知識か → いいえ。運用実務で必須。
ひっかけ5: 変更後確認は任意か → 不適切。品質保証の必須手順。
