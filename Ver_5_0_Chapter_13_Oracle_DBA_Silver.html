第13章の学習目的

第13章は、参照性能を高める索引、オブジェクト名の抽象化を行うシノニム、連番生成を担うシーケンスを扱う。いずれも構文は短いが、設計を誤ると性能劣化、命名混乱、重複キー事故へ直結する。試験では「索引が有効になりにくい条件」「PUBLIC SYNONYMの意味」「NEXTVAL/CURRVALの挙動」が狙われる。実務では、索引追加前の実行計画確認、シノニムの責務分離、シーケンスの欠番許容設計が必須である。到達点は、3要素を暗記ではなく運用上のトレードオフ込みで説明できる状態にすることである。

重要: 索引・シノニム・シーケンスは便利だが、乱用すると保守性と性能が同時に崩れる。

13.1 索引（INDEX）の定義

索引は特定列の検索効率を改善するための補助構造である。表全体を毎回走査する代わりに、索引経由で候補行を絞ることでI/Oを削減する。試験では「索引は検索を速くするが、DML時は更新負荷が増える」という両面理解が必須である。実務では検索頻度が高く選択性の高い列に作成し、なんでも索引化しない判断が求められる。索引は魔法ではなく、クエリ特性とデータ分布に合致したときに効果が出る道具である。

13.2 索引作成と使われ方

索引は`CREATE INDEX`で作成する。単一列・複合列のどちらを選ぶかは、WHERE条件や結合条件の実態に依存する。複合索引では列順序が重要で、先頭列が使われない検索では効果が落ちる。試験では構文と合わせて、LIKE先頭ワイルドカードや関数適用で索引利用が低下する点が出題される。実務では作成後に実行計画を確認し、期待通り利用されるかを検証することが必須である。

CREATE INDEX idx_emp_dept_hire
ON employees(department_id, hire_date);

13.3 索引の制限とアンチパターン

索引は万能ではない。低選択性列（例: 性別フラグ）に索引を張っても効果が薄く、更新負荷だけ増えることがある。`WHERE UPPER(col)=...` のように列へ関数を直接適用すると通常索引が効きにくくなる。試験ではこの種の「索引が使われにくいSQL」を見抜く問題が出る。実務のアンチパターンは「遅いSQLが出るたび索引追加」で、索引過多によりINSERT/UPDATE/DELETEが遅くなる。索引はクエリ改善・統計情報・設計改善とセットで最適化するべきである。

注意: 索引追加は副作用を伴う変更。読み取り性能だけで評価しない。

13.4 シノニム（SYNONYM）

シノニムはオブジェクトの別名を定義し、長いスキーマ修飾名を簡略化する。`PRIVATE SYNONYM`は作成者スキーマ内、`PUBLIC SYNONYM`は全体公開である。試験では公開範囲の違いと、シノニムが権限を付与する機能ではない点が重要である。実務ではシノニムを参照抽象化に使えるが、乱立すると実体追跡が困難になる。運用では命名規約と管理責任者を明確にし、参照先変更の影響を追える状態を維持することが必要である。

CREATE SYNONYM emp FOR hr.employees;
CREATE PUBLIC SYNONYM dept FOR hr.departments;

13.5 シーケンス（SEQUENCE）

シーケンスは重複しない連番を生成するオブジェクトで、主キー採番に広く使われる。`NEXTVAL`で次値取得、`CURRVAL`は同一セッションで一度NEXTVAL実行後に参照可能となる。試験ではこの順序制約が頻出である。実務ではトランザクションロールバック後も取得済み番号は戻らないため、欠番は通常仕様として扱う。連番に業務意味を持たせると欠番問題で混乱するため、識別子と業務番号を分離設計するのが安全である。

CREATE SEQUENCE seq_orders
START WITH 1000
INCREMENT BY 1
CACHE 20
NOCYCLE;

13.6 シーケンスの運用注意点

シーケンスでは`CACHE`設定により性能が向上するが、インスタンス障害時に未使用番号が飛ぶ可能性がある。`NOCACHE`は番号連続性を期待しやすいが性能面の不利が出る。試験ではCYCLE/NOCYCLE、MAXVALUE/MINVALUEなどオプション比較が問われる。実務では「採番の一意性」が目的であり「完全連番」を厳格要件にしないことが重要である。どうしても連番帳票が必要な場合は、発番専用管理と欠番取扱規程を別途整備する。

13.7 辞書ビューで確認

作成後は辞書ビューで定義確認する。索引は`USER_INDEXES`と`USER_IND_COLUMNS`、シノニムは`USER_SYNONYMS`、シーケンスは`USER_SEQUENCES`で確認できる。試験ではどの辞書ビューが何を保持するかの対応が問われる。実務では作成SQLだけでなく確認SQLを変更手順に含めると、定義漏れや環境差異を早期検知できる。オブジェクト管理は「作成したつもり」ではなく「確認済み」で初めて完了である。

SELECT sequence_name, increment_by, cache_size, last_number
FROM user_sequences
ORDER BY sequence_name;

13.8 典型エラーと修正

失敗1: 低選択性列へ無差別索引。修正: 実行計画とデータ分布で判断。
失敗2: CURRVALを初回参照。修正: 先に同一セッションでNEXTVAL実行。
失敗3: PUBLIC SYNONYM乱立。修正: 公開対象を最小化し規約管理。
失敗4: 連番欠番を障害扱い。修正: 一意性目的へ要件再定義。

13.9 実務運用パターン

推奨運用は、索引追加前に対象SQLと実行計画を記録し、追加後に改善効果とDML影響を比較する方式である。シノニムは参照抽象化のために限定利用し、PUBLICは最小限に抑える。シーケンスは主キー一意性確保に集中し、欠番は許容仕様として文書化する。試験対策では構文暗記に加えて、なぜその設定が必要かを説明できるようにすることで応用問題に強くなる。第13章の本質は、便利機能を安全に運用する設計判断力である。
