第6章の学習目的

第6章は、明細行をそのまま読む段階から「意味のある集計値を作る」段階へ進む章である。実務では部門別平均、件数、売上集計などKPIの基礎が集約SQLで作られるため、ここで誤ると経営判断まで誤る。試験でもCOUNTの差分、GROUP BY制約、HAVINGの評価位置、NULL除外挙動が頻出で、文法暗記だけでは対応できない。第6章の目標は、どの列を集約し、どの列をグループキーにするかを論理的に説明し、SQL結果の妥当性を件数ベースで検証できる状態に到達することである。

重要: 集計SQLは「見た目の数字」ではなく「意思決定の根拠」。1行の誤りが方針を誤らせる。

6.1 グループ関数の定義

グループ関数は複数行を1値へ集約する関数群で、COUNT、SUM、AVG、MAX、MINが中核である。単一行関数と異なり、入力は集合で出力は集約値となる。定義上の重要点は、どの行集合を集約対象にするかがSQL全体の意味を決める点である。WHEREで先に行を絞るか、HAVINGで集約後に絞るかで結果は変わる。実務では、集計単位を誤ると同じ指標名でも中身が異なるため、グループ関数は式より文脈で理解する必要がある。

6.2 COUNT(*) と COUNT(col)

COUNT(*)は行数を数え、COUNT(col)はNULLを除いた非NULL行数を数える。この差は試験の定番論点であり、実務でも監査件数不一致の原因になる。例えば「登録件数」をCOUNT(col)で算出すると、NULL行が除外され想定より少なく見える。要件が「全件数」か「有効値件数」かを明示し、関数選択を固定しなければならない。集計式は短いが意味差が大きいため、定義書にCOUNTの種類を明記する運用が有効である。

SELECT COUNT(*) AS all_rows,
       COUNT(commission_pct) AS non_null_comm
FROM employees;

6.3 GROUP BY

GROUP BYは集約単位を定義する句であり、同じキー値を持つ行をひとつのグループとして扱う。GROUP BYに含まれない非集約列をSELECTするとORA-00979が発生する。これは制約ではなく、集約結果の一意性を守るための仕様である。実務では、キー粒度が粗すぎると情報が潰れ、細かすぎると指標が分散するため、業務要件に合う粒度設計が必要になる。GROUP BYは文法ではなく「何を1単位として語るか」の定義である。

SELECT department_id, AVG(salary) AS avg_sal
FROM employees
GROUP BY department_id;

6.4 HAVING

HAVINGは集約後のグループに対する条件句であり、集約値を使った絞り込みに使う。WHEREは行を絞る、HAVINGはグループを絞るという役割分離が基本である。実務ではHAVINGへ行条件を入れてしまい、無駄に集約して性能を落とすケースが多い。試験ではWHEREとの違いが頻出で、評価段階を理解していないと誤答しやすい。HAVINGを使う時は「この条件は集約後でしか判定できないか」を確認するのが定石である。

SELECT department_id, AVG(salary) AS avg_sal
FROM employees
GROUP BY department_id
HAVING AVG(salary) >= 9000;

6.5 WHEREとHAVINGの責務分離

WHEREは集約前、HAVINGは集約後の条件である。これを混同すると件数と性能の両方が崩れる。例えば「退職者除外」はWHEREで行い、「平均給与9000以上」はHAVINGで行うべきである。すべてHAVINGへ寄せると、不要行まで集約してから捨てるためコストが増える。試験ではこの責務差を選択肢で問う問題が多く、実務ではクエリレビュー時の最重要チェック項目になる。条件を配置する前に「判定対象は行かグループか」を必ず言語化することが重要だ。

6.6 集約時のNULL挙動

SUM、AVG、COUNT(col)、MAX、MINは基本的にNULLを計算対象から除外する。COUNT(*)のみNULLを含む全行を数える。この差を理解せずに指標を作ると、欠損データが見えなくなる。実務ではNULL件数を別指標として出す運用が有効で、品質監視に直結する。試験でもNULL除外は定番で、式を見た瞬間にNULLの影響を想起できるかが得点を左右する。

6.7 疑似列（ROWID / ROWNUM）

ROWIDは行の物理的な位置識別子、ROWNUMは取得順に付与される疑似列である。ROWNUMはORDER BY適用前に評価される文脈があるため、上位N件抽出で誤解されやすい。実務ではROWIDを更新対象特定に使う場面があるが、永続キー代替として使うべきではない。試験では疑似列の用途差と制約が問われるため、通常列と同等に扱わないことが重要である。

SELECT rowid, employee_id
FROM employees
WHERE rownum <= 5;

6.8 典型エラー（ORA-00979等）

ORA-00979: GROUP BYにない非集約列をSELECTした場合に発生。修正は集約化またはGROUP BY追加。
論理エラー: WHEREとHAVINGの配置誤りで件数が変わる。修正は条件責務の再分離。
件数誤解: COUNT(col)を全件数として使う。修正はCOUNT(*)との使い分け明示。

6.9 実務集計パターン

実務では「前処理WHERE」「集約GROUP BY」「閾値HAVING」「出力ORDER BY」の順で組み立てると再利用しやすい。まず不要行を除外し、次に集約粒度を定義し、最後に閾値条件を掛ける。このパターンを標準化するとレビュー効率が上がる。さらに件数検証用SQLを並行作成しておくと、集計結果の妥当性確認が早い。集約SQLは単発で書くのではなく、検証手順込みでテンプレート化するべきである。
