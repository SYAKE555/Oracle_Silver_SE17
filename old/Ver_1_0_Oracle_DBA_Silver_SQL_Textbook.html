1. リレーショナル・データベースの概要

1.1 データベースの役割とタイプ1.2 リレーショナルモデル1.3 SQLの概要
実務ミニケース: 顧客台帳統合で主キー設計を誤ると、同一人物の二重登録が監査で発覚します。

データベースは「大量データから必要情報を正確に取り出す仕組み」です。DBMSは整合性（壊れないこと）を保証します。

例え: 紙の台帳を1万冊持つ倉庫で検索する代わりに、索引つき電子台帳から条件検索するイメージです。

1.1 データベースの役割とタイプ

方式特徴向いている場面
階層型親子1対多の木構造固定的な階層データ
ネットワーク型多方向参照複雑な参照関係
リレーショナル型行と列、SQLで操作業務システム全般

1.2 リレーショナルモデルとは

  • 表（relation）は行（tuple）と列（attribute）で構成される。
  • 主キーは重複しない識別子、外部キーは他表との整合を担保する。
  • NULLは「値なし/不明」であり、0や空文字とは別概念。

1.3 SQLの概要

分類主な文用途
DQLSELECT取得
DMLINSERT, UPDATE, DELETE, MERGEデータ操作
DDLCREATE, ALTER, DROP, TRUNCATE構造定義
TCLCOMMIT, ROLLBACK, SAVEPOINTトランザクション制御
章の要点: 「表」「キー」「NULL」「SQL分類」を曖昧にしないことが後続章の理解速度を決めます。

2. SQL SELECT文を使用したデータの取得

2.1 SELECT基本構文2.2 列の取得2.3 列計算と列別名2.4 行選択（WHERE）
実務ミニケース: 画面APIでSELECT *を使うと列追加時にフロントが壊れます。列は明示取得します。

2.1 SELECT文の基本構文

SELECT employee_id, last_name, job_id
FROM employees;

実務: APIレスポンス、画面一覧、CSV出力はこの構文を土台に組み立てます。

2.2 列の取得

SELECT *
FROM employees;

SELECT employee_id, last_name, salary
FROM employees;
本番運用では SELECT * は列増減の影響を受けやすいので極力避ける。

2.3 列の計算と列別名

SELECT last_name,
       salary * 12 AS annual_salary,
       salary * (1 + NVL(commission_pct, 0)) AS total_income
FROM employees;

例え: 列別名は「帳票の見出し名」。SQL内部名と表示名を切り分ける。

2.4 行の選択（WHERE）

SELECT employee_id, last_name, salary
FROM employees
WHERE department_id = 50
  AND salary >= 8000;
確認: AND と OR は優先順位が異なるため、混在時は括弧を付ける。
章の要点: 「必要列だけ取得」「計算列を別名で可読化」「WHEREは早期絞り込み」が基本。

3. データの制限とソート

3.1 ソートと行数制限3.2 ORDER BY3.3 OFFSET/FETCH3.4 置換変数
実務ミニケース: 上位N件のダッシュボードは ORDER BY なしだと毎回順序が変わります。

3.1 SELECT文の基本構文（ソートと行数制限）

行数制限は、必ずソート順を決めた上で使う。順序未指定では結果が毎回変わりうる。

3.2 並べ替え（ORDER BY）

SELECT last_name, salary, commission_pct
FROM employees
ORDER BY salary DESC, commission_pct NULLS LAST;

3.3 SQL行制限（OFFSET句、FETCH句）

SELECT employee_id, last_name, salary
FROM employees
ORDER BY salary DESC
FETCH FIRST 10 ROWS ONLY;
SELECT employee_id, last_name, salary
FROM employees
ORDER BY salary DESC
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

3.4 置換変数

-- SQL*Plus系クライアント
SET VERIFY ON
DEFINE dept_id = 30
SELECT last_name, salary
FROM employees
WHERE department_id = &dept_id;
実務: バッチ用SQLを手動実行するとき、置換変数で対象期間や部署を切り替えると安全。
章の要点: 「ORDER BYで順序固定→OFFSET/FETCHで範囲切り出し」が定石。

4. 単一行関数を使用した出力のカスタマイズ

4.1 単一行関数とグループ関数4.2 行ごとの計算
実務ミニケース: 氏名検索は表記ゆれが多いため、UPPER/TRIMで正規化して検索漏れを防ぎます。

4.1 単一行関数とグループ関数

分類例戻り値
単一行関数UPPER, SUBSTR, ROUND, NVL1行ごとに1値
グループ関数COUNT, SUM, AVG, MAX, MIN複数行を集約した1値

4.2 行ごとの計算

SELECT employee_id,
       INITCAP(last_name) AS last_name_fmt,
       SUBSTR(email, 1, 6) AS email_prefix,
       ROUND(salary * 1.08, 0) AS salary_sim
FROM employees;
暗記: SUBSTR は1始まり、INSTR は見つからないと0。
章の要点: 単一行関数は「表示整形」「検索条件の正規化」「簡易計算」で多用される。

5. 変換関数と条件式の使用

5.1 データ型の変換5.2 NULLの処理5.3 条件式とDECODE関数
実務ミニケース: 文字列日付比較は環境差で事故になります。TO_DATEで型を揃えます。

5.1 データ型の変換

SELECT TO_CHAR(hire_date, 'YYYY-MM-DD') AS hire_ymd,
       TO_DATE('2026-04-01', 'YYYY-MM-DD') AS d
FROM dual;

5.2 汎用関数によるNULL処理

SELECT employee_id,
       salary * (1 + NVL(commission_pct, 0)) AS amount1,
       COALESCE(bonus_amt, allowance_amt, 0) AS amount2
FROM comp_plan;

5.3 条件式とDECODE関数

SELECT employee_id,
       CASE
         WHEN salary >= 12000 THEN 'A'
         WHEN salary >= 8000 THEN 'B'
         ELSE 'C'
       END AS grade,
       DECODE(job_id, 'IT_PROG', 'IT', 'OTHER') AS job_grp
FROM employees;
実務: 画面表示用の区分値変換は SQL 側で行うと、アプリ実装が単純化される。
章の要点: 変換関数は「型整合」、NULL関数は「計算停止防止」、CASEは「分類」に使う。

6. 行使用した集計データのレポート

6.1 グループ化と集計6.2 グループ関数6.3 グループ化の構文6.4 まとめ6.5 ROWNUM/ROWID
実務ミニケース: 部署KPI会議では、GROUP BY粒度を先に合意しないと数字が一致しません。

6.1 / 6.2 グループ化とグループ関数

SELECT department_id,
       COUNT(*) AS emp_count,
       SUM(salary) AS total_sal,
       AVG(salary) AS avg_sal
FROM employees
GROUP BY department_id;

6.3 グループ化の構文（HAVING）

SELECT department_id, AVG(salary) AS avg_sal
FROM employees
GROUP BY department_id
HAVING AVG(salary) >= 9000;
頻出エラー: ORA-00979（GROUP BYにない列をSELECT）。

6.5 疑似列 ROWID / ROWNUM

SELECT rowid, employee_id, last_name
FROM employees
WHERE rownum <= 3;
章の要点: 集計の順序（FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY）を固定して覚える。

7. 複数の表からのデータの表示

7.1 結合の考え方7.2 内部結合7.3 外部結合7.4 クロス結合7.5 自然結合7.6 その他の結合7.7 まとめ
実務ミニケース: 未所属社員監査はLEFT JOINで欠損行を残して抽出します。

7.1 結合の考え方

結合は「別表の列を横に並べる」処理。キー列が一致条件。

7.2 内部結合（INNER JOIN）

SELECT e.last_name, d.department_name
FROM employees e
INNER JOIN departments d
  ON e.department_id = d.department_id;

7.3 外部結合（OUTER JOIN）

SELECT e.last_name, d.department_name
FROM employees e
LEFT OUTER JOIN departments d
  ON e.department_id = d.department_id;

7.4 クロス結合（デカルト積）

SELECT e.employee_id, d.department_id
FROM employees e
CROSS JOIN departments d;

7.5 自然結合 / 7.6 その他の結合

SELECT last_name, department_name
FROM employees
NATURAL JOIN departments;
実務: NATURAL JOINは結合列が暗黙になるため、保守性を重視するならON/USINGを優先。
章の要点: 「一致行だけ返すか」「片側の欠損行も残すか」を先に決める。

8. 副問合せを使用した問合せの解決

8.1 副問合せ8.2 相関副問合せ
実務ミニケース: 部門平均超え抽出は相関副問合せで条件を説明可能にします。

8.1 副問合せ

SELECT last_name, salary
FROM employees
WHERE salary > (
  SELECT AVG(salary)
  FROM employees
);

8.2 相関副問合せ

SELECT e.last_name, e.salary, e.department_id
FROM employees e
WHERE e.salary > (
  SELECT AVG(i.salary)
  FROM employees i
  WHERE i.department_id = e.department_id
);
比較: NOT IN はNULL混入で0件化し得る。安全側なら NOT EXISTS を検討。
章の要点: 単一行/複数行/相関の違いを演算子とセットで覚える。

9. 集合演算子の使用

9.1 種類9.2 規則9.3 まとめ
実務ミニケース: 統合前の明細保持はUNION ALL、重複除去が必要な確定帳票のみUNIONを使います。

9.1 集合演算子の種類

演算子意味重複
UNION結合除去
UNION ALL結合保持
INTERSECT共通部分除去
MINUS差集合（左−右）除去

9.2 集合演算の規則

  • 各SELECTで列数が同じこと。
  • 対応列の型が互換であること。
  • ORDER BYは原則、最後のSELECT全体に1回指定。
SELECT employee_id FROM employees WHERE department_id = 10
UNION ALL
SELECT employee_id FROM employees WHERE department_id = 20;
章の要点: 速度優先ならUNION ALL、重複排除が必要な場面だけUNIONを使う。

10. DML文を使用した表の管理

10.1 行の追加/更新/削除10.2 マルチテーブルINSERT10.3 MERGE10.4 トランザクション制御
実務ミニケース: 本番更新は件数確認→SAVEPOINT→更新→差分確認→COMMITを運用標準にします。

10.1 行の追加・列の更新・行の削除

INSERT INTO departments (department_id, department_name)
VALUES (290, 'Ops');

UPDATE employees
SET salary = salary * 1.03
WHERE department_id = 50;

DELETE FROM departments
WHERE department_id = 290;

10.2 マルチテーブル・インサート

INSERT ALL
  WHEN salary >= 10000 THEN INTO high_sal (emp_id, salary) VALUES (employee_id, salary)
  WHEN salary < 10000 THEN INTO low_sal  (emp_id, salary) VALUES (employee_id, salary)
SELECT employee_id, salary FROM employees;

10.3 MERGE文

MERGE INTO sales_target t
USING ( SELECT 10 dept_id, 1200000 amt FROM dual ) s
  ON (t.dept_id = s.dept_id)
WHEN MATCHED THEN
  UPDATE SET t.target_amt = s.amt
WHEN NOT MATCHED THEN
  INSERT (dept_id, target_amt) VALUES (s.dept_id, s.amt);

10.4 トランザクション制御

UPDATE employees SET salary = salary * 1.02 WHERE department_id = 80;
SAVEPOINT sp1;
DELETE FROM employees WHERE employee_id = 9999;
ROLLBACK TO sp1;
COMMIT;
章の要点: 「どこまで戻せるか」を先に設計してから更新系SQLを書く。

16. 異なるタイムゾーンでのデータの管理

16.1 タイムゾーン16.2 日時データ型16.3 タイムゾーン関数16.4 期間データ型
実務ミニケース: 海外拠点連携はTZ付き型保存 + 表示時変換を徹底して時刻齟齬を防ぎます。

16.1 タイムゾーンについて

複数拠点運用では、時刻の比較基準（UTC/ローカル）を統一しないと監査で齟齬が出る。

16.2 日時データ型

型特徴
DATE日付＋時刻（秒まで）
TIMESTAMP小数秒まで
TIMESTAMP WITH TIME ZONETZ情報付き
TIMESTAMP WITH LOCAL TIME ZONEDB TZで保存、セッションTZで表示

16.3 日時データ型データ用タイムゾーン関数

SELECT CURRENT_DATE AS current_date_local,
       CURRENT_TIMESTAMP AS current_ts_local,
       CURRENT_TIMESTAMP AT TIME ZONE '+00:00' AS current_ts_utc
FROM dual;

16.4 期間データ型（INTERVAL）

SELECT CURRENT_TIMESTAMP + INTERVAL '90' MINUTE AS plus_90m,
       CURRENT_TIMESTAMP + INTERVAL '2' DAY AS plus_2d
FROM dual;
実務: 保存はTZ付き、画面表示時に業務TZへ変換する方針が事故防止に有効。
章の要点: 「保存時の基準TZ」と「表示時のTZ変換」を分離して設計する。

章別ケーススタディ（実務例・確認問題つき）

ここでは各章の論点を、実運用で起きる状況に置き換えて確認します。試験対策だけでなく、手を動かして再現できることを重視してください。

ケース1: 1章（RDB基礎）

状況: 複数部署でExcel管理していた顧客台帳を統合する。重複や更新漏れが多発している。

  • 主キーを自然キーにするか、代理キーにするかを先に決める。
  • 「未入力」と「不明」をNULLで混在させない運用ルールを作る。
  • 参照整合性（外部キー）を切ると、後で結合不能データが増える。
確認問題: 「NULLは0と同じか」「主キーにNULLは許可されるか」を説明できるか。

ケース2: 2章（SELECT/WHERE）

状況: 月次レポートで「営業部かつ売上100万以上」の抽出が毎回ブレる。

SELECT emp_id, dept_id, amount
FROM sales_monthly
WHERE dept_id = 50
  AND amount >= 1000000;
考え方: まずWHEREで対象行を絞る。表示都合の整形は後段で行う。

ケース3: 3章（ソート/行制限）

状況: ダッシュボードの上位10件表示がリロードのたびに変わる。

SELECT order_id, order_amount, created_at
FROM orders
ORDER BY order_amount DESC, order_id ASC
FETCH FIRST 10 ROWS ONLY;
注意: ORDER BYなしでFETCHすると再現性が担保できない。

ケース4: 4章（単一行関数）

状況: 顧客名の表記ゆれ（大文字小文字、全角半角）で検索漏れが発生。

SELECT customer_id, UPPER(customer_name) AS customer_name_u
FROM customers
WHERE UPPER(customer_name) LIKE '%TOKYO%';
確認問題: 関数を列側に適用した場合の索引利用性を説明できるか。

ケース5: 5章（型変換/条件式）

状況: 文字列日付を比較してしまい、月跨ぎで並び順が崩れた。

SELECT order_id
FROM orders
WHERE order_date >= TO_DATE('2026-04-01', 'YYYY-MM-DD');
考え方: 比較対象は型を揃える。暗黙変換に依存しない。

ケース6: 6章（集計）

状況: 部署別平均給与を出したいが、個人名を同時表示してORA-00979。

SELECT department_id, AVG(salary) AS avg_salary
FROM employees
GROUP BY department_id
HAVING AVG(salary) >= 9000;
注意: GROUP BYに含めない列をSELECTへ出すとエラー。

ケース7: 7章（結合）

状況: 部署未所属社員をレポートに含める必要がある。

SELECT e.employee_id, e.last_name, d.department_name
FROM employees e
LEFT JOIN departments d
  ON e.department_id = d.department_id;
考え方: 欠損行を残したい側をLEFT/RIGHTで選ぶ。

ケース8: 8章（副問合せ）

状況: 「部門平均を超える社員」を部署ごとに抽出したい。

SELECT e.employee_id, e.department_id, e.salary
FROM employees e
WHERE e.salary > (
  SELECT AVG(i.salary)
  FROM employees i
  WHERE i.department_id = e.department_id
);
確認問題: 単一行副問合せと複数行副問合せで使う演算子の違いを説明できるか。

ケース9: 9章（集合演算子）

状況: 複数キャンペーン対象者リストを統合し、重複扱いを使い分けたい。

SELECT customer_id FROM campaign_a
UNION ALL
SELECT customer_id FROM campaign_b;
考え方: 明細件数が必要な集計前処理ではUNION ALLを優先。

ケース10: 10章（DML/トランザクション）

状況: 一括更新で想定外件数を更新したため、途中時点へ戻したい。

UPDATE orders SET status = 'CLOSED' WHERE shipped_at IS NOT NULL;
SAVEPOINT before_close;
DELETE FROM orders WHERE order_date < ADD_MONTHS(SYSDATE, -60);
ROLLBACK TO before_close;
注意: COMMIT後はSAVEPOINTへ戻れない。

ケース11: 11章（DDL）

状況: 既存表にNOT NULL制約を追加したいが、既存データにNULLが混在。

  • 1. NULLデータ補正
  • 2. 制約追加
  • 3. 影響SQLの再試験
確認問題: DROP TABLE と TRUNCATE の違い（ログ/復旧観点）を説明できるか。

ケース12: 12章（ビュー）

状況: 複数チームへ同じ参照ロジックを配布したい。

CREATE OR REPLACE VIEW v_monthly_sales AS
SELECT dept_id, SUM(amount) AS total_amount
FROM sales_monthly
GROUP BY dept_id;
考え方: 共通ロジックをビューへ寄せると、修正点を1か所に集約できる。

ケース13: 13章（索引/シーケンス）

状況: 「顧客番号検索が遅い」。実行計画で全表走査が選ばれている。

  • 検索条件の列に索引があるか確認する。
  • 選択率が低すぎる列へ索引追加しても効かない場合がある。
  • 採番はシーケンスで衝突回避する。
確認問題: 索引追加で更新性能が落ちる理由を説明できるか。

ケース14: 14章（権限管理）

状況: 人事異動で担当変更。アクセス権の棚卸しが未整備。

CREATE ROLE sales_reader;
GRANT SELECT ON sales_monthly TO sales_reader;
GRANT sales_reader TO analyst_user;
REVOKE sales_reader FROM analyst_user;
注意: 直接権限の乱発は監査時の追跡を難しくする。

ケース15: 15章（辞書ビュー）

状況: 障害調査で「どの表に対象列があるか」すぐ知りたい。

SELECT owner, table_name, column_name
FROM all_tab_columns
WHERE column_name = 'ORDER_STATUS'
ORDER BY owner, table_name;
考え方: 辞書ビュー検索は、調査時間を最短化する第一手。

ケース16: 16章（タイムゾーン）

状況: 海外拠点と日本拠点で「同じ時刻」の認識がズレる。

SELECT order_id,
       created_at,
       created_at AT TIME ZONE '+09:00' AS created_at_jst
FROM orders_tz;
確認問題: DATE型とTIMESTAMP WITH TIME ZONE型の使い分けを説明できるか。

学習チェック（試験・実務共通）

  • SELECTの処理順（FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY）を言える。
  • NULL比較で = NULL を使わず IS NULL を使える。
  • JOIN時に結合条件漏れ（デカルト積）を検知できる。
  • 副問合せで単一行/複数行の演算子を正しく選べる。
  • UNIONとUNION ALLの違いを件数・性能で説明できる。
  • 更新系SQLの前に対象件数確認SQLを必ず打てる。
  • COMMIT前にROLLBACK戦略（SAVEPOINT含む）を決められる。
  • 主キー/外部キー/一意制約/検査制約の役割を説明できる。
  • GRANT/REVOKE/ROLEで最小権限設計を実践できる。
  • 辞書ビューを使ってテーブル構造・制約を自己調査できる。
  • TZ付きデータ型を使うべき業務要件を説明できる。
  • 公開時にHTTPSで配信し、教材本文が静的HTMLのみで閲覧できる。

公式仕様ベース補強（19c/21c）

Oracle 公式仕様で誤解されやすい点を、試験対策と実務運用の両面で整理した補強ノートです。

論点公式仕様の要点実務での使い方
MERGE1文で更新/挿入を分岐。1行を同一文で複数回更新できない性質（deterministic）。UPSERT用途で有効。投入元のキー重複を事前排除する。
集合演算子列数一致と型グループ一致が必須。優先順位が絡む場合は括弧で明示。保守SQLは型を揃え、列別名を固定して可読性を担保する。
トランザクションCOMMITで確定。DDL実行時は暗黙COMMITが発生。DDL/DMLを同一変更作業に混在させない。
SEQUENCENEXTVALはロールバックしても戻らず欠番は仕様。業務上の連番保証が必要なIDには使わない。
辞書ビューUSER_/ALL_/DBA_ で可視範囲が異なる。障害調査テンプレを定義して初動対応を短縮する。
日時TZ型TIMESTAMP WITH LOCAL TIME ZONE は保存時と表示時でTZ解釈が分かれる。保存型の方針を先に固定し、表示は業務TZで統一する。
実務注意: NLS設定差・TZ差・権限差は本番前に検証環境で再現テストする。
